## S0. Conventions

### S0.1 Names and numbers

Languages and libraries. The server is C++20, built with CMake. Its libraries are Jolt Physics, Recast and Detour, Luau, uWebSockets, bitsery, zstd, meshoptimizer, cgltf and Tracy. The gateway, the bake service and the measures library are Python 3.12.

Step. A u64 counter that starts at 0 and adds 1 every 50 ms. World time in seconds is the step divided by 20. No game logic reads a wall clock.

Handle. Every object is named by a 64-bit handle: a 32-bit slot and a 32-bit generation. A slot is reused after its object is destroyed, and its generation is then raised by 1, so a handle to the old object no longer matches. Handle 0 means none.

Ids. Players, models, scripts, terms, grants, groups, plots and requests have u32 ids, given out in order and never reused. Records in the event record have u64 ids.

Text form. Outside the server a handle is written o:slot.generation, and other ids as a letter, a colon and the number: p for a player, m for a model, s for a script, t for a term, g for a grant, r for a request.

Hashes. Content is named by the SHA-256 of its bytes, written as 64 hex characters.

Units. Positions are meters, as three 32-bit floats, in a right-handed frame with Z up. Rotations are unit quaternions (x, y, z, w). Every other quantity is a 64-bit float in SI base units.

Bytes. Binary formats are little-endian. Structured binary data is written with bitsery.

### S0.2 Module boundaries

Each workstream is one library with one public header. A function receives the tables it reads or writes as arguments. No function takes the whole server or the whole store. Calls are direct, and no virtual interface is added for the sake of a boundary.

server/store/    tables and the sparse column (S1)

server/step/     step loop, queues, timers, intents (S2)

server/react/    registry, dispatch, script host (S3, S4)

server/perm/     presets, grants, the check, offers (S9)

server/space/    Jolt and Detour glue, zones, sight, illuminance

server/net/      WebSocket endpoint and replication (S6)

server/record/   event record writer (S7)

server/snap/     snapshot writer and loader (S10)

gateway/         MCP server and CLI (S5)

bake/            bake service and workers (S8)

measure/         measures library and adapters (S11)

### S0.3 Config

One file, config.toml, holds every constant written in capitals in this tab, such as STEP_HZ = 20. Code never contains these numbers. Every value is Proposed and is expected to change as the prototype shows what it should be. There are two kinds. A protective limit exists only so that the server survives overload, a runaway script or untrusted input. It is set far above normal use, and reaching one is written to the event record. A tuning value trades one cost for another. Nothing is capped for its own sake: work that does not fit in a step waits for the next one and is not refused, and a caller can raise any default that shapes a response. The constants and the reason for each:

STEP_HZ = 20. Tuning. The reasons are in design point 5 of the Technicals tab.

STEP_MARGIN_MS = 5. Tuning. Time kept free at the end of a step, so that one slightly long handler does not cause an overrun.

HANDLER_MS = 5. Protective. Stops a script that is stuck in a loop from stalling the step. It counts the CPU time the step thread spends on the run, not time on the clock (S4.3). An ordinary handler takes microseconds.

SCRIPT_KB = 4096. Protective. Stops one script from exhausting memory.

EVENT_QUEUE_MAX = 1000000. Protective. About 100 MB of queued events. Reaching it means that something is feeding itself.

SEND_SOFT = 256 KB and SEND_HARD = 4 MB. Protective. The server must not hold unbounded data for a viewer that cannot keep up.

BAKE_S = 20 and BAKE_MB = 2048. Protective. A model program is untrusted code.

MODEL_MAX_M = 256 and TRIS_MAX = 200000. Protective. They bound what one model can cost every viewer's browser.

CAPACITY_GRID = 256. Tuning. The number of voxels along a model's longest side when its capacity is measured (S8.4). A larger number is more accurate and costs more memory and bake time. 256 keeps the grid under about 70 MB.

MAILBOX_MAX = 100. Protective. From design point 14: at the cap a gift bounces back to the sender.

STREET_WIDTH_M = 100, PORT_SPACING_M = 1000, BLOCK_M = 72, WAY_M = 8, LOT_FRONT_M = 16 and TERRAIN_TILE_M = 256. Tuning. The land layout of S13.1. The Street and its ports follow Snow Crash, and terrain tiles are the size of Second Life's regions.

POOL_LOTS_MIN = 4. Tuning. The engine surveys more land when fewer lots of a kind than this remain in the pool (S13.1).

CELL_M = 32, ENTER_CELLS = 2 and LEAVE_CELLS = 3. Tuning. The reasons are in S6.1.

REPL_EVERY = 2 and REPL_DELAY_MS = 150. Tuning. The reasons are in S6.3.

SIGHT_M = 30, REACH_M = 1.5 and DIM_LUX = 10. Tuning. Starting values for how far a body sees in full, how far it reaches, and when a thing counts as unlit.

THINGS_MAX = 40 and EVENTS_PER_RESPONSE = 40. Tuning. Defaults that keep a response short for the agent's sake. A caller can ask for more.

GAP_CAPTURES = 3 and CAPTURE_M = 10. Tuning. Enough examples of a gap, and enough of its surroundings, for an elaborator to work from.

AUTHORS_MAX = 8. Format. It keeps a record small, and an overflow is flagged in the record.

SNAP_EVERY_S = 60 and SNAP_KEEP = 10. Tuning. From design point 15.

SWING_SPEED = 6 m/s. Tuning. A rough speed for a swung hand tool.

MIN_ACTIONS = 20 and WIKI_WORLDS = 40. These belong to the frozen measure definitions in S11 and are not limits on the system.

### S1.1 The sparse column

Every table that is keyed by an object and belongs to one term is this one structure.

template <class V> struct SparseColumn {

  std::vector<uint32_t> slot_of;   // dense position -> object slot

  std::vector<V>        value;     // dense position -> value

  std::vector<uint32_t> pos_of;    // object slot -> dense position, or NONE (0xFFFFFFFF)

};

get(slot): read pos_of[slot]. NONE means the object has no entry.

set(slot, v): if absent, push to both dense arrays and record the position.

erase(slot): move the last dense entry into the hole, fix its pos_of, and pop the end.

To visit every holder, walk the dense arrays from 0 to their size.

pos_of grows with the objects table.

### S1.2 Objects

One row per instance, as parallel arrays indexed by slot.

struct Objects {

  std::vector<uint32_t> generation;

  std::vector<Vec3>     position;      // meters

  std::vector<Quat>     rotation;

  std::vector<uint32_t> model;         // model id

  std::vector<uint32_t> material;      // id of a term of kind material

  std::vector<uint32_t> owner;         // player id

  std::vector<uint32_t> maker;         // player id; never changes

  std::vector<uint64_t> created_step;  // never changes

  std::vector<uint32_t> group;         // group id, or 0

  std::vector<uint32_t> preset;        // permission bits (S9.1)

  std::vector<uint32_t> plot;          // plot id, or 0

  std::vector<Handle>   parent;        // container or attachment, or none

  std::vector<uint32_t> flags;

  std::vector<uint32_t> params;        // index of the instance's parameter values

  std::vector<uint32_t> free_slots;

};

Flag bits: 1 static, 2 dynamic (simulated by Jolt), 4 body (a player's body), 8 scripted motion, 16 held, 32 proxy (its asset is not ready), 64 no-copy, 128 in escrow.

### S1.3 Values, properties and processes

struct Value { uint8_t type; union { double f; int64_t i; bool b; Handle h; }; };   // 16 bytes

std::vector<SparseColumn<Value>>   properties;   // indexed by term id

std::vector<SparseColumn<Process>> processes;    // indexed by term id

struct Process { double v0; uint64_t step0; double rate, lo, hi; };

Only terms whose source is state or setting have entries in properties (S3.1).

Intrinsic values are on the material record (S3.3). Measured values are in the manifest of the model's asset (S8.5), except mass, which is computed from the asset's volume and the model's material (S8.4). A read of a term on an object goes to exactly one place, chosen by the term's source. For a setting it tries the instance, then the model, then the plot and world defaults. Nothing is copied to the instance.

A process is a state quantity that changes steadily. Its value at step s is clamp(v0 + rate * (s - step0) / 20, lo, hi). Setting a new rate first folds the current value into v0 and step0.

### S1.4 Relations

struct Relation { SparseColumn<SmallVec<Handle,4>> out, in; };   // one per relation term

An edge from a to b is stored in out[a] and in in[b]. The engine maintains four built-in relations: base.contains, base.supports, base.attached_to and base.in_zone. Authored relations, such as base.wired_to, are changed by edits and handlers.

### S1.5 Shared quantities

struct Part   { Handle from; double amount; };

struct Shared { double total; SmallVec<Part,4> parts; };

std::vector<SparseColumn<Shared>> shared;          // indexed by term id, keyed by the subject's slot

SparseColumn<SmallVec<SubjectTerm,2>> gives_to;    // keyed by the contributor's slot

contribute(from, subject, term, amount): replace the part from that contributor, or remove it when the amount is 0. Recompute total with the term's combine rule (S3.2). If total changed, mark (subject, term) dirty (S2.3).

gives_to lists, for each contributor, the (subject, term) pairs it contributes to. It exists so that destroying an object removes its parts without searching every shared quantity in the world. Together with relations it is the only second index in the store.

For a term whose record names a relation in along (S3.1), a read on object o uses shared[t][o] if it exists, and otherwise shared[t][s] for the first s in out[o] of that relation. A change on s wakes s and every object in in[s].

### S1.6 Text

struct Text { uint32_t name, description, writing; SmallVec<uint32_t,2> details; };   // ids into a string pool

One array of Text for models and one SparseColumn<Text> for instances. An instance with no entry shows its model's text. details are the entries added by elaboration.

### S1.7 Players, ledger and plots

struct Player {

  uint32_t id; Handle body; uint64_t key_hash; uint32_t roles;   // roles: 1 elaborator, 2 architect

  std::vector<Handle>   inventory;                              // objects whose parent is the body

  std::vector<uint32_t> groups;                                 // sorted group ids

  std::vector<uint32_t> grants_held, grants_given;              // grant ids

  std::vector<Handle>   mailbox;
  std::vector<Json>     notices;                              // notices waiting for login, oldest first

};

std::vector<int64_t> ledger;   // balance per player id, in the smallest money unit

struct Plot { uint32_t id, owner, group, preset; PlotKind kind; Rect bounds; std::vector<uint32_t> banned; };   // kind: street, alley or lot (S13.1)

Money is whole numbers. A payment subtracts and adds in one call, and does nothing if the payer's balance is short. Player 0 is root (S9.2), and its account is the money account. Its balance is unlimited and is not stored: a payment from root creates money, needs a spend grant that root gave, and is never short, and a payment to root removes the money from circulation.

### S1.8 Who writes what

store creates and destroys objects and owns every table's memory.

react writes properties, processes, shared, gives_to and authored relations.

space writes position, rotation and the four built-in relations.

perm writes owner, group, preset, grants, offers, mailboxes and the ledger.

net, record and snap only read.

## S2. Step loop

Status: Trying.

Figure S2. The order of work in one step.

### S2.1 Order of one step

1. Raise the step counter. Swap in the inputs that arrived from the network threads since the last step.

2. Foreground lane. Take, in this order: work left over from earlier steps, oldest first; timers due at this step, as events; inputs in arrival order. After each item, drain (S2.3) before taking the next.

3. Background lane. Take items for as long as the step's handler time lasts, and at least one item per step, draining after each.

4. Space. Advance Jolt by one collision step of 50 ms and update the Detour crowd. Copy the transforms of the bodies that moved into Objects. Turn contacts, zone entries and exits, and support changes into events for the next step's foreground lane.

5. Perception. For each agent whose surroundings changed, rebuild its pending observation (S5.3).

6. Replication. On every second step, encode and send (S6.3).

7. Record. Hand this step's event records to the writer thread (S7). Start a snapshot if one is due (S10.1).

8. Sleep until the next 50 ms boundary. If the step overran, start the next one at once and count the overrun.

### S2.2 Inputs

An input is an action from a session, a finished bake, or a session opening or closing. An action is applied in four moves: find the action's declaration (S4.5), run the permission check (S9.3), run the handlers, write the event record. A denied action runs no handler.

### S2.3 Draining

queue: FIFO of Work { kind: event or watch; target: handle; term: id; value; from: Origin }

Origin: { cause: record id; root: record id; authors: up to AUTHORS_MAX ids; oldest: seconds }   copied from the record that caused the work (S7)

dirty: map from (subject slot, term id) to the value its handlers last saw

drain():

  while queue is not empty and the step's budget is not spent:

    w = pop the front of queue

    for each handler that dispatch(w) returns (S3.4), in order:

      run it; it may set, contribute, emit and act (S4.2)

      each emit pushes one event

      each changed watched value pushes one watch, unless one for that (subject, term) is already queued

  whatever is left stays in the queue for the next step

Budget. Handlers may use all the time the step has left: 50 ms, less the recent cost of the other phases (an average over the last 20 steps), less STEP_MARGIN_MS = 5. There is no cap on the number of runs. Work that does not fit waits for the next step and is never refused.

A watch fires only if the value differs from the value in dirty, which is then updated. A value that changed and changed back within one drain fires nothing.

The queue holds at most EVENT_QUEUE_MAX = 1000000 events. This is a protective limit against running out of memory, far above normal use. An event pushed beyond that is dropped and written to the event record with kind system and name overflow. Watches are not counted against the limit and are never dropped. There is at most one queued watch for each (subject, term), so their number is bounded by the world itself, and a changed watched value is always handled, late if need be.

### S2.4 Timers

A hierarchical timer wheel with 4 levels of 256 slots. The lowest level has one slot per step. An entry is { due step, target handle, event term, one Value, Origin }. Origin is four values copied from the record that set the timer: its id as the cause, its root, its authors and its oldest (S7). Queued work carries an Origin in the same way. Timers and queued work are saved in snapshots with it, so an effect that fires later, or after a restore, still knows which player's action it descends from, and no old record is ever read to find out. Each step, the entries in the lowest level's current slot become events. When a level wraps, the next level's current slot is spread into the level below. A timer whose target has been destroyed is dropped when it comes due.

A process (S1.3) with a watch that names a threshold gets one timer at the step where its value will cross the threshold. The timer is recomputed whenever the rate is set, and carries the Origin of the handler run that set it.

### S2.5 Intents

An intent is one row kept on a body: { id, kind, goal, state }. The prototype has one kind, move_to, with a point or an object as its goal. Each step the space module advances it through the Detour crowd. It ends as arrived, blocked, cancelled or replaced by a new intent. Each ending is an event to the body and a line in the session's next response.

## S3. Term registry and rules

Status: Trying.

### S3.1 Term record

struct Term {

  uint32_t id; std::string name;   // namespace.name, such as base.density

  Kind kind;                       // quantity, flag, event, relation, action, material

  Source source;                   // quantity and flag only: intrinsic, measured, state, setting

  int8_t dim[8];                   // exponents of m, kg, s, A, K, mol, cd, and one custom dimension

  bool conserved;

  Combine combine;                 // none, sum, max, any, share_equal, share_priority

  uint32_t along;                  // a relation term the quantity is read along, or 0

  uint32_t owner; std::string description; std::vector<Input> inputs;   // inputs: actions only

};

The registry is one file, registry.json. It holds the terms, the materials, and the rules with their versions and whether each is switched on. It changes only through registry edits by players with the elaborator or architect role, and each edit is written to the event record. Every edit writes the whole registry as a new file in the asset store, registry/HASH.json, and the server keeps the hash of the current one. Old versions are never deleted, so a snapshot can always load the registry it was taken with. A term's id is its position in the file and never changes.

Names. A proposer gives a short name, and the system puts the proposer's namespace in front. The namespace base is reserved for terms that ship with the engine.

Duplicates. On a proposal the registry returns the existing terms with the same kind, dimensions, combine rule and source. The proposer must name one of them as the same term or state that none fits, and the answer is stored with the new term.

Dimensions. Luau has no units, so every host call that takes a quantity names its term (S4.2). When a script is loaded, each contribute and set is checked: the term must exist, have the right kind, and be one the script declares.

### S3.2 Combine rules

sum: the total is the sum of the parts. max: the largest part. any: 1 if any part is nonzero.

share_equal and share_priority divide a scarce supply. The subject has supply parts and demand parts on two paired terms. share_equal gives each demander the smaller of its demand and supply / n, then divides what is left among those still short, and repeats until nothing changes. share_priority serves demanders in the order of a priority setting until the supply runs out. A demander reads its own allocation with get_share (S4.2).

### S3.3 Materials

A material is a term of kind material with a map from intrinsic terms to values, such as base.density = 7850 for steel. The base registry ships generic, wood, steel, glass, ceramic, stone, water, fabric and plastic. Each has base.density, base.hardness, base.conductivity, base.flammable and base.transparent.

### S3.4 Rules and dispatch

Figure S3. How one piece of work finds its handlers.

struct Handler { uint32_t script, fn, author, version; bool enabled; };

struct Triggers {                                      // one per trigger term

  FlatMap<uint32_t, Handler>             by_material;  // material id -> the one active world rule

  SmallVec<FlagRule,4>                   by_flag;      // { flag term the object must have, Handler }

  FlatMap<uint32_t, Handler>             by_model;     // model id -> the model script's handler

  FlatMap<uint32_t, SmallVec<Handler,1>> by_instance;  // object slot -> instance script handlers

};

A trigger term is an event term, an action term, or a quantity, flag or relation that scripts watch. When an edge of a watched relation is added or removed, both of its ends are woken, and the handler is given the other end and whether the edge was added.

dispatch(work), for target object o and trigger t, returns in this order: by_material[material(o)] if it is enabled; each by_flag entry whose flag o has; by_model[model(o)]; by_instance[slot(o)]. All of them run, and none cancels another.

One active rule per selector and trigger. Adding a world rule whose selector and trigger match an existing entry replaces it, raises version, and appends the old entry to rules_history. Restoring an old version is the same operation.

Switching a rule off sets enabled to false and changes nothing else.

Catch-up. When a rule that watches a quantity is added or switched on, copy shared[t].slot_of once into a work list. Each step the background lane takes its items from the front of that list. An item is skipped if the slot's generation has changed, the object no longer holds the quantity, or the selector does not match.

Gaps. If dispatch returns nothing for a watch on a shared quantity, add 1 to gap_count[(term, material)]. For the first GAP_CAPTURES = 3 of each pair, write a capture and open a request with no requester (S12). If the work came from a player's action, the action's result is not_modeled.

## S4. Scripts

Status: Trying.

### S4.1 File format

A script is one Luau file that returns a table. This one is the script of a pump model.

local function update(self)

  local on = self:get('base.on') and self:get('base.supplied_power') >= self:setting('aq.rated_power')

  local tank, old = self:related('base.contains', 'in')[1], self.state.tank

  if old and old ~= tank then self:contribute(old, 'aq.aeration', 0.0) end   -- withdraw from the tank it has left

  if tank then self:contribute(tank, 'aq.aeration', on and 4.0 or 0.0) end

  self.state.tank = tank

end

return {

  kind = 'model',                                   -- 'instance', 'model' or 'rule'

  applies_to = nil,                                 -- rules only: { material = 'base.steel' } or { flag = 'base.flammable' }

  watches = { 'base.supplied_power', 'base.on', 'base.contains' },   -- quantities, flags and relations that wake this script

  contributes = { 'aq.aeration' },                  -- terms it may contribute

  slots = { },                                      -- rights it asks for (S9.2)

  actions = { ['base.switch'] = { right = 'use' } },

  on = {

    ['base.supplied_power'] = update,

    ['base.on'] = update, ['base.contains'] = update,

    ['base.switch'] = function(self, sender, args, caller) self:set('base.on', not self:get('base.on')) end,

  },

  tests = { },                                      -- rules need at least one (S12.3)

}

### S4.2 Host calls

self:get(term): the value of a term on this object (S1.3), or the total of a shared quantity (S1.5).

self:setting(term): an authored setting.

self:set(term, value): state terms only, on this object and its parts only.

self:rate(term, per_second, lo, hi): turns a state quantity into a process (S1.3).

self:contribute(subject, term, amount): subject is this object, a handle returned by self:related, or a subject it already contributes to, so that it can withdraw with an amount of 0. term must be listed in contributes. A contribution stays until the script withdraws it or its object is destroyed. A script that follows a relation must therefore withdraw from the old subject when the relation changes, as the pump in S4.1 does.

self:get_share(subject, term): this object's allocation under a share rule.

self:related(relation, 'out' or 'in'): the handles at the other end of the relation. Two handles are equal when they name the same object.

self:emit(target, event, value): target is this object, one of its parts, or a handle from self:related or from the event being handled.

self:act(action, target, args): an ordinary action, checked against the script's grants (S9.3).

self:after(seconds, event, value): a timer that sends the event to this object.

self:parts() and self:move_part(part, position, rotation), for scripted motion such as fish.

self.state: a table of numbers, booleans, strings and handles that is kept between runs. It counts against the script's memory limit.

world.raycast(from, to) and world.near(self, radius): exact queries. Their cost counts against the run's time limit. The VM cannot interrupt a native call, so each query checks the run's deadline itself as it collects results and stops early when the deadline passes. The run is then cut off as in S4.3.

self:plot(id) returns a plot's record as in S5.1, self:plots() the ids of all plots, and self:plot_objects(id) the things standing on a plot that are not declared parts of another thing. They read only what any player may inspect, and their cost counts against the run's time limit.

self:now() returns world time and self:random() a number from a generator seeded per object. Nothing else exists: no files, no network and no other clock.

### S4.3 Limits

Two protective limits stop a runaway script from stalling the step or exhausting memory. A handler run is cut off once it has used HANDLER_MS = 5 ms of CPU time on the step thread, by the VM's interrupt callback and by the deadline check inside the native queries of S4.2, which that callback cannot reach, and a script's memory is capped at SCRIPT_KB = 4096. Both are far above what an ordinary handler needs. Why CPU time and not time on the clock: a busy host can pause the step thread for several milliseconds in the middle of an ordinary handler, and a limit on the clock would cut that handler off for the host's load, not for anything the script did. A busy host makes the world slower through the step budget (S2.3), as a busy Second Life region runs its scripts slower, and does not cut scripts off. Reading the clock is cheap and reading the thread's CPU time is not, so each check compares the clock with a deadline first. Only when that deadline has passed does it read the CPU time: if the run has used less than HANDLER_MS, the deadline moves out by what is left, and otherwise the run is cut off. Changes made before a cut-off stay, and a record with kind system and name cutoff is written. A run that ends in a script error is treated the same way, with the name error. Nothing is rolled back. Undoing a handler's changes would need every change to be staged or logged for undo, and version 2 leaves that machinery out. Only exchanges of valuables are all or nothing (S9.4). There is one VM per region. Each script is a sandboxed thread with its own environment, and host objects are tagged userdata that hold a handle.

### S4.4 Loading

The bake service compiles the file, runs its top level once in a fresh VM with a 50 ms limit, and reads the returned table. It rejects a script that names an unknown term, watches or contributes a term of the wrong kind, declares an action with an unknown right, sets a term whose source is not state, or has kind rule without applies_to or tests. The accepted declaration is stored as script.json beside the source, so the server never runs the top level to learn it.

### S4.5 Actions

An action name is a term of kind action. Its inputs and their units are on the term, so one name has one signature in a world. A script's actions table lists the actions its object accepts and the right each one needs.

A handler is called as handler(self, sender, args, caller). For an action on an object, sender is the body or script object that acted; for an action a body declares on itself, it is the thing selected; for an event, it is the event's sender. args is the action's arguments or the event's value. For an action, caller says who called it: 'p:N' for a player, or { script = 's:N', on = handle } for a script. It names the caller and grants nothing: the handler still acts only under its own grants, so a lease can accept its terms only from the plot's owner without acting with the owner's authority. A handler for an event or a timer gets no caller.

A body's script declares the body's actions in the same way. The humanoid body script declares the physical verbs base.strike, base.push, base.pour and base.throw. Its handler for base.strike reads the held object's mass and hardness and emits base.impact to the target with the energy in joules as its value: 0.5 * mass * SWING_SPEED^2, with SWING_SPEED = 6 m/s.

An action called on an object that does not declare it is not refused. The server sends the action's term to the object as an event with right use, so a world rule can answer it. If nothing handles it, the result is not_modeled. The cost is the same as for a declared action: one permission check and one dispatch, which is at most four lookups. It is paid once per action a player makes and never per step, and a repeated gap adds one to a counter and writes nothing more after the first three captures.

## S6. Wire protocol

Status: Trying.

Figure S6. One endpoint, two kinds of frame.

There is one WebSocket endpoint, /ws. Text frames carry JSON control messages. Binary frames carry replication. Browser viewers and the gateway use the same endpoint, and the gateway asks for no binary frames.

### S6.1 Interest grid

The region is cut into square cells of CELL_M = 32 on the ground plane. Height is ignored. Why 32: with the 5 by 5 block below, a viewer receives everything within 64 to 80 m, which covers what a camera at street level can make out. Cells of 16 m would have a walker cross a border about every 11 seconds, each crossing costing keyframes. Cells of 64 m would send every viewer a 320 m square, most of it out of sight.

A viewer in cell (i, j) subscribes to every cell within ENTER_CELLS = 2 of it, a block of 5 by 5. It unsubscribes from a cell only when the cell is more than LEAVE_CELLS = 3 away, so an object near a border does not flicker.

Each cell has one stream. Everything sent on a stream goes to all its subscribers as the same bytes.

An object belongs to the cell that contains its position. An object with a footprint wider than one cell belongs to a region-wide stream that every viewer subscribes to.

### S6.2 Control messages (text frames)

These are shown without the quotes that JSON needs.

client: { t: hello, version: 1, key: '...', mode: play | watch | debug, binary: true | false }

client: { t: join, version: 1, name: 'Mira', persona: '...' }   server: { t: joined, player: p:9, key: '...' }, then the session continues as after hello

server: { t: welcome, session: 31, player: p:7, body: o:17.1, step: 48210, step_hz: 20, cell_m: 32, assets: 'https://host/assets/' }

client: { t: do, id: 5, action: 'base.switch', target: o:812.1, args: { } }

server: { t: result, id: 5, ... }                      the fields of S5.2

client: { t: look, id: 6 }   { t: inspect, id: 7, target: o:812.1 }   { t: actions, id: 8 }   { t: cancel, id: 9 }

server: { t: obs, id: 6, ... }                         the fields of S5.3

server: { t: event, kind: arrived | blocked | heard | answered | changed, ... }   pushed to play sessions; the gateway queues them

server: { t: bye, reason: replaced | shutdown | bad_key | refused }

server: { t: terrain, tile_m: 256, tiles: [[i, j], ...] }   sent after welcome and whenever tiles are added; tile (i, j) covers i * tile_m <= x < (i + 1) * tile_m and j * tile_m <= y < (j + 1) * tile_m, flat at z = 0

### S6.3 Replication messages (binary frames)

The first byte is the message type.

1 CELL_KEYFRAME  cell_i:i16 cell_j:i16 step:u32 count:u16 Entity*

2 CELL_DELTA     cell_i:i16 cell_j:i16 step:u32 removed:u16 local:u16* added:u16 Entity* changed:u16 Change*

3 CELL_DROP      cell_i:i16 cell_j:i16

Entity { local:u16 handle:u64 asset:[32 bytes] params:u64 flags:u8 pos:3 x i32 rot:u32 states:u8 (term:u16 value:f32)* }

Change { local:u16 mask:u8 [pos: 3 x zigzag varint] [rot:u32] [asset:[32 bytes] params:u64] [states:u8 (term:u16 value:f32)*] [flags:u8] }

local is a number the cell gives an object when it enters, and reuses after the object leaves. A client applies a delta in the order it is written: removals, then additions, then changes. An object that enters a cell, by being placed there or by moving in, is sent in added, with its handle and its absolute position. A local freed by a removal may be given to an addition in the same message.

Positions are whole centimeters from the cell's corner. In a keyframe they are absolute. In a delta they are the difference from the last value sent on that stream, as zigzag varints, so a slow mover costs one byte per axis. Why centimeters: a centimeter is below what a viewer notices at human scale, and at 10 updates a second anything slower than 6.3 m/s moves at most 63 units between updates, which fits in one byte.

Rotation is in smallest-three form: 2 bits for the index of the largest component and 10 bits for each of the other three. An object whose model says it faces the way it moves sends no rotation.

states carries the few state terms that a model's manifest lists as replicated, such as on or open.

Replication runs every REPL_EVERY = 2 steps, which is 10 times a second. Why 10: viewers draw 150 ms behind and interpolate, so updates 100 ms apart always leave two updates around the moment being drawn, even when one arrives 50 ms late. Sending every step would double the bytes for motion that interpolation already smooths. Agents do not use replication at all. Only objects marked dirty since the last send are written, and a cell with nothing dirty sends nothing.

A keyframe is built only in the replication phase of a replication step, after that step's delta for the cell has been encoded, and from the same whole-centimeter values that the delta leaves as the stream's last values. A new subscriber gets that keyframe, does not get that step's delta, and gets every delta after it. A viewer that asks to join between replication steps waits for the next one, which is at most 50 ms away.

Clients draw REPL_DELAY_MS = 150 behind the newest update and interpolate between the two updates around that time.

### S6.4 Slow viewers

uWebSockets reports the bytes buffered for each socket. Above SEND_SOFT = 256 KB the server stops sending that viewer deltas and marks its cells stale. When the buffer drains, it sends fresh keyframes, built by the same rule as for a new subscriber (S6.3). Above SEND_HARD = 4 MB it closes the socket. Nothing is dropped silently.

### S8.1 Submitting

The bake service speaks HTTP on the gateway's host and takes the player's API key. The CLI wraps it: amb submit model cup.py, and amb submit script pump.luau.

POST /bake/models    { source, params?, material?, text: { name, description, writing? } }   -> 202 { job }

POST /bake/scripts   { source }            -> 200 { script: s:44, hash }  or  422 { errors }

GET  /bake/jobs/ID   -> { status: queued | baking | done | failed, model: m:210, hash, measured, errors }

A bake produces an asset. An asset is geometry only, and everyone who submits the same source and parameters shares it. A model is a row in the server, made for each submission: { model id, asset hash, material, author, group, text, script }. The author, or any member of the model's group, may change the model's script, settings and text. Two players who submit the same file get two models that point at one asset, each with its own author, text and material. A finished bake is an input to the step loop (S2.2). The model row is added, and any proxy that was waiting for it is swapped for the real asset.

### S8.2 Model programs

A model is one Python file.

from amb.shapes import hollow_cylinder

PARAMS = { 'height': (0.10, 0.05, 0.30), 'radius': (0.04, 0.02, 0.10) }   # default, min, max in meters

MATERIAL = 'base.ceramic'

def build(p):

    return hollow_cylinder(radius=p['radius'], height=p['height'], wall=0.004, floor=0.006)

build returns one build123d solid or a compound of solids, in meters, standing upright, with its base on Z = 0 and centered on the Z axis.

amb.shapes has box, slab, cylinder, sphere, hollow_box, hollow_cylinder and stair. Any other build123d code is allowed.

Optional names: SITES, the points where a body or an object attaches, such as a seat. PARTS, the named solids that scripts can move. SCRIPT, the hash of the model's script. REPLICATED, the state terms sent to viewers.

### S8.3 What a bake does, in order

1. Hash the source, the parameters as canonical JSON, and BAKE_VERSION. Nothing else enters the hash, because nothing else changes the geometry. If the asset store has that hash, skip to adding the model row.

2. Fork a child from the warm worker and run build(p) with limits of BAKE_S = 20 seconds and BAKE_MB = 2048.

3. Check. The bounds are within MODEL_MAX_M = 256 on each axis. Every solid is closed. A model that uses stair has a rise of 0.12 to 0.20 m, a run of at least 0.25 m and a width of at least 0.8 m.

4. Tessellate with OCCT at a linear tolerance of 1 mm or 0.2% of the largest dimension, whichever is larger. Fail above TRIS_MAX = 200000 triangles.

5. Make three levels of detail with meshoptimizer: 100%, 40% and 10% of the triangles.

6. Make the collision shape. A model placed as static gets a Jolt mesh shape from the 40% level. A model that can be held or simulated gets a convex hull of at most 64 points.

7. Measure (S8.4).

8. Write the files (S8.5) and report done. The step loop then adds the model row (S8.1).

### S8.4 Measured properties

size is the bounding box and volume comes from OCCT. Both are stored in the asset's manifest. mass is not stored. It is the asset's volume times the density of the model's material, computed when it is read, so the same shape in steel and in wood has two masses, and a change to a material's density takes effect at once.

supports is each planar face that faces up (its normal within 10 degrees of +Z) and has at least 0.01 square meters, as a polygon with its height.

capacity is in cubic meters. For a shape made only with amb.shapes it is computed exactly from the shape's parameters: the inside volume of a hollow_box or a hollow_cylinder, and 0 for the others. For any other shape it is found by flooding a voxel grid from the outside, lowest first:

h = largest dimension / CAPACITY_GRID                 the voxel edge in meters, with CAPACITY_GRID = 256

a voxel is solid if any triangle of the lod0 mesh touches it (triangle-box overlap test); pad the grid with one empty layer on every side

level[v] = infinity for every empty voxel

for every empty voxel v on the outer faces of the grid: level[v] = z(v); push v into a min-heap keyed by level

while the heap is not empty:

  v = pop the voxel with the lowest level

  for each of v's 6 neighbors n that is empty and still has level[n] = infinity:

    level[n] = max(level[v], z(n)); push n

capacity = h^3 * the number of empty voxels whose level is finite and greater than z(v)

level[v] is the height that liquid at v must reach before it can run out of the grid. A voxel that lies below its level is inside a basin. A solid block has a capacity of 0, and an upright cup has its inside volume up to the rim. Marking every voxel that the surface touches keeps a wall closed however thin it is, so a tank with 10 mm glass does not leak through its own walls. The price is that each inner surface counts as up to one voxel thicker than it is, so the result is low by at most one voxel layer along the inside. Voxels that the flood never reaches are inside solid material and are not counted. The grid has at most 256 voxels on its longest side, about 17 million in all, whatever the size of the model.

### S8.6 Sandbox

## S9. Permissions and trade

Status: Trying.

### S9.1 Presets

verbs, one bit each:  0 use, 1 take, 2 move, 3 edit, 4 copy, 5 transfer, 6 destroy

object preset:        bits 0-6 everyone, bits 8-14 group, bits 16-22 next owner

plot preset:          bits 0-2 everyone (build, enter, run scripts), bits 8-10 group; transfer and return are never preset

The owner has every verb.

### S9.2 Grants

struct Grant {

  uint32_t id, issuer, parent;     // parent is a grant id, or 0

  Holder   holder;                 // a player id, or a script id with the object it is installed on

  Scope    scope;                  // one object | the issuer's objects | the issuer's objects on one plot | one plot's land | all land (root only) | the issuer's wallet | the issuer's avatar

  uint32_t verbs;                  // object verbs; or land verbs: bit 0 build, 1 enter, 2 run scripts, 3 transfer, 4 return; for all land, object verbs in bits 0-6 and land verbs in bits 8-12; or bit 0 spend; or bit 0 animate, bit 1 camera

  int64_t  cap, spent; uint64_t period_steps, period_start;

  uint64_t expires_step;           // required when the verbs include spend or the holder is a script

};

FlatMap<GrantKey, uint32_t> grant_by_key;   // key = (holder, scope); at most one grant per key

To create a grant, the issuer must own the scope, or hold a grant on it that has no parent and covers the new one: the same or more verbs, the same or a larger cap, and the same or a later expiry. A grant made from another grant shares that grant's allowance and does not add to it: spending under the child is counted against the parent as well. A grant on a plot's land carries build, enter, run scripts, transfer and return. Root is player 0. It owns every plot in the pool and every way (S13.1), and its account is the money account (S1.7). It gives grants only in the start file, and only root can give a grant on all land, which covers every lot's land and everything on every lot, lots surveyed later included. A grant on all land covers an object scope on any lot, so its holder may pass on a grant on one object, which stays when the object leaves the lot. No player can act or issue as root: step 1 of the check never matches root, and no one, an architect included, can revoke a grant root gave. An architect may revoke any other grant. The architects group is controlled by root, so no game action changes its membership; only an operator command does (S5.4).

Revoking a grant removes it and every grant that names it as parent.

A sale or transfer of an object removes every grant scoped to that object and tells the old owner which ones. A plot changes owner only by an accepted plot offer (S9.4), or by going back to the pool, which its owner or a holder of transfer on its land may do. When a plot goes back to the pool, everything still on it is returned to its owners. A change of owner removes every grant on the plot's land and on the old owner's objects there that the old owner issued, with their children, and tells the old owner which ones. Grants root gave stay.

An owner, or a holder of transfer on the land, may split a lot in two along a whole-meter line inside it, or join two lots with the same owner that share a whole edge and together form a rectangle. A split keeps the plot's id for the half at the lower x or y and gives the other half a new id with the same owner, group, preset and banned list. Every grant whose scope names the plot is copied for the new plot, children included, and things belong to the half they stand on. A join keeps the lower id. Grants whose scope names the other plot are removed with their children, and their issuers are told which. Both close any open offer on the plots. Ways are never split or joined.

A timer at expires_step removes an expired grant.

Installing a script turns each of its slots into one grant whose holder is that script on that object.

### S9.3 The check

check(actor, verb, object) returns allowed or a reason. It runs once per action. It does not run for perception or for a script changing its own object.

1. actor is the object's owner                                           -> allow

2. the preset's everyone bits have the verb                              -> allow

3. the object has a group, the preset's group bits have the verb,

   and actor.groups contains that group (binary search)                  -> allow

4. g = grant_by_key[(actor, object)] exists and has the verb             -> allow, after the cap test

5. g = grant_by_key[(actor, owner's objects)] has the verb               -> allow, after the cap test
   or g = grant_by_key[(actor, owner's objects on this plot)] has the verb -> allow, after the cap test
   or, on a lot, g = grant_by_key[(actor, all land)] has the verb          -> allow, after the cap test

6. otherwise                                                             -> deny { need, on, why }

Land actions (build, enter, run scripts, transfer, return) use the plot's preset in the same way, then a grant on that plot's land, then, on a lot, a grant on all land, after one lookup in the plot's banned list. Transfer and return are never in a preset.

The cap test, for spend, on a grant g: if step - period_start >= period_steps, set spent to 0 and period_start to step. The test passes if spent + amount <= cap. If g has a parent, run the same test on the parent. Allow only if every test passes, and then add the amount to spent on g and on its parent. Two scripts each given 100 a week out of a player's grant of 100 a week therefore spend out of the same 100.

The check allocates nothing. The only link it follows is from a grant to its parent, which is one step, because a grant that has a parent cannot be passed on again.

### S9.4 Offers, trades and gifts

struct Offer { uint32_t id, seller, buyer_or_0, plot_or_0; Holder maker; Handle goods; int64_t price; uint64_t expires_step; };

Creating an offer puts the goods in escrow: the parent becomes none and the escrow flag is set. The owner does not change.

Accepting is one input, and it names max_price, the most the buyer will pay. Test that the offer asks no more than max_price, and test the buyer's balance. Then move the price on the ledger, set the goods' owner and parent, clear the goods' grants and delete the offer. If a test fails, nothing changes. The seller, or the maker of the offer, may change the price of an open offer, and max_price means a buyer is never charged more than they agreed to.

A direct trade is two offers that each name the other player. Either player changing their side clears both confirmations.

A give to an absent player appends to that player's mailbox, up to MAILBOX_MAX = 100. Beyond that the give is refused and the sender keeps the item. The mailbox is emptied into the inventory at login.

A notice to a player with no play session, such as which grants a change of a plot's owner removed, waits in the mailbox and is sent as an event at the player's next login, oldest first. Notices do not count against MAILBOX_MAX. At most MAILBOX_MAX notices wait; a newer one pushes out the oldest, and the first notice delivered says how many were pushed out.

Returning an object sends it to its owner, and a return never fails. The plot's owner, or a holder of return on the plot's land, may return any object on the plot that someone else owns, except a body, and except an object whose owner holds build on the plot's land, directly or through a passed-on grant, until that grant is gone. The object is first detached from anything that is not one of its own parts, and any body sitting or standing on it is let go and falls. It then goes into its owner's inventory if the owner's body is present, otherwise into the mailbox; MAILBOX_MAX does not apply. Its grants are kept, and it takes its parts and contents with it. The banned list keeps bodies out.

An offer may sell a lot instead of an object: plot_or_0 is then the lot's id and goods is none. The offer is made by the lot's owner or by a holder of transfer on its land, and maker records which. A lot is not escrowed. Accepting checks that the lot's owner is still the seller and that the maker may still transfer the lot, then moves the price and transfers the lot as in S9.2, all or nothing. The price goes to the seller. For a pool lot the seller is root, so the money leaves circulation. A buyer may accept from anywhere, and a lot's open offer is shown in its record (S5.1). Ways are never offered.

## S10. Snapshot file

Status: Proposed.

Figure S10. The parts of a snapshot file and what is rebuilt on loading.

header:   magic 'AMBSNAP1' | format:u32 = 1 | runtime_version:string | step:u64 | registry_hash:[32 bytes] | sections:u32

section:  tag:4 bytes | length:u64 | payload

footer:   xxh64 of everything before it

The sections, in this order: OBJS (S1.2), PROP (properties and processes), RELS, SHRD (shared and gives_to), TEXT, PLYR (players, ledger, plots and groups), GRNT (grants and offers), SCST (script state), TIMR (timers), QUEU (queued work and intents), REQS (elaboration requests), RAND (the random seed of each object) and MOVE (for each dynamic object and each body: its handle, its linear and angular velocity, and whether it is asleep). Jolt's StateRecorder is not used, because it restores state only onto bodies that already exist under the same ids, and positions and rotations are already in Objects. Each payload is the table written with bitsery, with a vector as its length followed by its elements. A sparse column is written as pairs of slot and value. Trigger tables, navigation tiles and collision structures are not saved.

### S10.1 Writing

At a step boundary the step thread writes every section into one reused buffer and notes the time it took. It hands the buffer to the writer thread, which compresses it with zstd at level 3, writes snap-STEP.amb.zst under a temporary name, and renames it. A periodic snapshot is taken every SNAP_EVERY_S = 60, and the last SNAP_KEEP = 10 are kept.

### S10.2 Loading

1. Check the magic, the format and the footer. Refuse a runtime_version that this binary does not list as loadable.

2. Load the registry version that the header's hash names, from registry/HASH.json in the asset store. Registry edits made after the snapshot are not part of the restored world. Load the scripts and manifests that the tables name from the asset store.

3. Read the sections into the tables.

4. Rebuild, in this order: the pos_of arrays; the trigger tables, from the registry and scripts; a Jolt body for every object, static or dynamic, from Objects and collision.bin, filling the space module's map from object to Jolt body as they are made; the velocities and sleep state of the moving ones, from the MOVE section; the navigation tiles; the paths of intents in progress.

5. Start stepping at the saved step plus 1.

A capture (S12.2) is a file in this format that holds a subset of the rows.

## S11. Measures

Status: Trying. These definitions are frozen. A change makes a new version number, and every result names the version it used. This is version 1.

Figure S11. From any world's record to the measures and the validation.

### S11.1 The minimal record and the adapter

The library is a Python package named measure. Each world has an adapter, a module with two functions.

def info() -> dict

    # name, t0, period_s, seed_actors, roles (optional), and classes: a map from action type to change, move, speak or look

def events() -> Iterator[dict]      # in time order

    # required: t (seconds), actor, type, object (or None)

    # optional: result, maker, created, kind, cause, root, authors, oldest, agent (false for an event no agent chose, such as a handler run)

The library fills in what a record does not give, in one pass over the events:

maker(object) is the given maker, and otherwise the actor of the first event on that object.

created(object) is the given time, and otherwise the time of the first event on that object.

kind(object) is the given kind, and otherwise the object itself.

class(event) is classes[type], and otherwise change.

authors(event) is the given set, and otherwise the actor and maker(object). oldest(event) is the given value, and otherwise created(object).

An actor listed in seed_actors is seed. Seed makers are removed from every author set, and seed objects are left out of lookback and novelty.

### S11.2 Definitions

An agent event is an event that an agent chose: every event, unless the adapter marks it agent: false. C is the set of events whose class is change and whose result is applied or missing. It includes events that no agent chose, such as handler runs. CA is the agent events in C. The period of an event is floor((t - t0) / period_s). An agent is active in a period if it has at least MIN_ACTIONS = 20 agent events in it. JSD(P, Q) = 0.5 * KL(P || M) + 0.5 * KL(Q || M) with M = 0.5 * (P + Q), logarithms to base 2, and 0 * log 0 = 0.

Acting share = |CA| / the number of agent events with class change, move, speak or look. Handler runs are in neither count, so a switch that sets off a thousand reactions counts once. It is not available when every event in a record has class change, because such a record logs only changes.

Loop rate. Write one agent's agent events in order as a_1 to a_n, with a_i = (type, object, result). a_i is looping if, for some k from 1 to 8, i >= 2k and the k events ending at a_i equal the k events before them. An agent's rate is its looping events divided by n. The run's value is the mean over active agents.

Cross-author share = the number of events in C whose authors set has 2 or more members, divided by the number of events in C that have an object. Beside it: the number of distinct pairs of authors that appear together in any authors set.

Causal lookback. For an event e in C with a non-seed object and t(e) > t0: L(e) = (t(e) - oldest(e)) / (t(e) - t0). Report the median and the 90th percentile of L.

Adopted novelty. A kind is new in period p if its first non-seed object was created in p. It is adopted if some event e in C acts on an object of that kind, has an actor (the root actor, where given) other than the kind's maker, and has t(e) <= created(kind) + 2 * period_s. The value for p is the number of kinds new in p that are adopted. Beside it: that number per 100 active agents.

Role divergence. For each active agent a in period p, q(a, p) is the distribution of its events in CA over types. The value for p is the mean of JSD(q(a, p), q(b, p)) over all pairs of active agents. It is not available with fewer than 2 types or fewer than 2 active agents.

Role coherence. On-role share is the share of an agent's events in CA whose type is in its role's list, averaged over the agents that have a role. Persistence is the mean, over agents active in both p and p - 1, of 1 - JSD(q(a, p), q(a, p - 1)).

Gap rate, for our world only: agent events with result not_modeled per 100 agent events.

### S11.3 Output

python -m measure ADAPTER writes report.json and periods.csv. report.json holds each measure for the whole run, the counts it was computed from, the definitions version, and not_available with a reason where a measure does not apply. periods.csv has one row per period.

### S11.4 Adapters

ours reads events.jsonl.zst (S7). A record of kind speech has class speak, an observation has class look, the action move_to has class move, and a record with changed true has class change. A record of kind handler is marked agent: false. A create record for a submitted model or script is an agent event of class change.

emergence reads one world per file. actor is name, type is tool_name, and object is target_agent where present and otherwise location. Its classes are a table in the adapter with one line per tool, written before any result is computed.

moltbook has the types post and comment. object is the post or comment replied to, and maker is its author. Every event has class speak, so acting share is 0 and C is empty. Loop rate applies. Cross-author share, lookback, novelty and the role measures are not available, because no event in the record changes the world, and the report says so.

onefthree reads the events file of a 1F3D9 daily snapshot. A use event has the thing used as its object.

wikipedia reads the MediaWiki history dump. actor is event_user_id, type is the event type with a revert as its own type, object is page_id, and created is page_first_edit_timestamp. The kind of a page in the Template or Module namespace is the page itself. Edits in talk namespaces have class speak and the rest have class change.

### S11.5 Validation procedures

One script, validate.py, runs both. Its first act is to write the definitions version and the expectations below to a file with a timestamp.

Wikipedia. A world is the set of articles in one category tree. Draw WIKI_WORLDS = 40 categories with a fixed random seed from the English Wikipedia categories that hold 500 to 5000 articles within two levels. For each world and each week of 2024, compute the measures and the summed pageviews. For each measure the statistic is the Spearman correlation between the week-to-week change in the measure and the week-to-week change in the logarithm of pageviews, pooled over worlds, with a 95% interval from 1000 bootstrap resamples of worlds.

Emergence World. A world is one season and model. Compute acting share, loop rate, role divergence, persistence and cross-author share. The expectations, from the published accounts: the world whose agents died of inaction has the lowest acting share; the world that fell into violence has the highest cross-author share; the world whose agents voted yes 98% of the time has the lowest role divergence. Report the table and whether each expectation held. With about a dozen worlds there is no significance test.

## S12. Elaboration records

Status: Proposed.

### S12.1 Requests

struct Request {

  uint32_t id, requester;            // requester is 0 for a gap found mid-chain

  uint32_t action, term, material;   // what was tried, and the gap's key

  Handle   target; Hash capture;

  Status   status;                   // open, claimed, answered, refused

  uint32_t claimed_by; uint64_t created_step, answered_step;

  Answer   answer;                   // a rule's script hash | a patch note | a detail's text id | a refusal's text id

};

A player's action request_model(note) creates a request from that player's last not_modeled result.

Elaborator actions need the elaborator role. requests(page) lists the open ones, explicit requests first and then gaps in order of gap_count. claim(id) takes one. answer(id, kind, payload) and refuse(id, text) close it.

Answering with a rule runs the rule's tests in a fixture (S12.3) and, if they pass, adds the rule to the registry (S3.4).

When a request with a requester is closed, that player's session gets an event of kind answered with the text to show.

### S12.2 Captures

A capture is a snapshot file (S10) that holds the target, every object in the requester's last observation, whether it was sent in full or in the short form of S5.3, the objects related to those by any relation, and their properties, shared quantities and text. For a gap found mid-chain it holds the objects within CAPTURE_M = 10 of the subject. It is stored in the asset store under its hash.

### S12.3 Fixtures and tests

amb fixture CAPTURE starts a server process from the capture, with no network clients and its own step counter. A rule's tests run there. The design calls the three parts given, when and then. The third is spelled expect in a script, because then is a reserved word in Luau.

tests = {

  { given  = { subject = 'target', contribute = { ['chem.corrosive_exposure'] = 2.0 } },

    when   = { steps = 200 },

    expect = { subject = 'target', term = 'base.integrity', below = 1.0 } },

}

For each test the fixture reloads the capture, applies given (contributions and state values on named subjects), runs when (a number of steps, or one action), and compares expect (a term's value on a subject: equals, above or below).

A rule is accepted only if every test passes with the rule and at least one test fails without it.

## S13. Land

Status: Trying.

The engine lays out and surveys land (S13.1). Everything else in this section is content: one land script, content/scripts/land.luau, the script of an ordinary model, on an object near Port Zero that an architect owns, holding root's grant on all land (S9.2). The engine provides plots, the layout, land grants, plot offers, splitting, joining, abandoning and returning (S9). Every name written land_... is a setting of that script, kept in world_settings next to base.rent_grace_days, and every default is Proposed. The script posts, as writing on its object, each owned lot's rent per day and how it was worked out, and each pool lot on offer with its price (S5.1). The purpose is to get land into the market fairly and to take money out of circulation, not to squeeze players.

### S13.1 Layout

Plot bounds are whole meters, so a plot is a set of 1 m by 1 m cells. A cell is named by its minimum corner (x, y), and its center is (x + 0.5, y + 0.5). Every plot has a kind: street, alley or lot. Street and alley plots are ways: root owns them, and they are never valued, charged, offered, split or joined. Their preset lets everyone enter and run scripts, and lets the architects group build.

The Street is the strip -STREET_WIDTH_M / 2 <= y < STREET_WIDTH_M / 2, along x. Port n is the point (n * PORT_SPACING_M, 0) for every integer n, so Port Zero is at the origin. A body that enters the world for the first time is placed at Port Zero. The monorail is content: architects build it on the Street and script it.

Land beyond the Street is cut into blocks BLOCK_M square. Block (i, j), for j >= 1, covers i * BLOCK_M <= x < (i + 1) * BLOCK_M and STREET_WIDTH_M / 2 + (j - 1) * BLOCK_M <= y < STREET_WIDTH_M / 2 + j * BLOCK_M, and block (i, -j) is its mirror south of the Street. In each block, an alley WAY_M wide runs the full depth of the block along its lower-x edge, and a back way WAY_M wide runs along the edge farthest from the Street, for the rest of the block's width. The rest is two rows of lots LOT_FRONT_M wide, each half the remaining depth. The row nearer the Street fronts the Street when |j| = 1, and otherwise the back way of the block before it; the far row fronts the block's own back way. With the defaults a block holds 8 lots of 16 m by 32 m. The Street piece of column i is the street plot i * BLOCK_M <= x < (i + 1) * BLOCK_M across the Street's width.

Surveying. For the pool, lots are of two kinds: Street lots, which front the Street, and back lots. Whenever fewer than POOL_LOTS_MIN lots of a kind are in the pool, at world creation or after a sale, the engine surveys one block: the unsurveyed block nearest Port Zero, by the distance from its center, that adds lots of that kind (|j| = 1 for Street lots) and whose neighbor toward the Street in the same column is surveyed or is the Street. Ties go north before south, then to the higher x. Surveying a block creates its alley, back way and lots as root's plots, the Street piece of its column if that is not there yet, and terrain under all of them. Plot ids follow survey order, so lower ids are nearer Port Zero. The seeded mode's start file names the lots it gives players by their minimum corners, and the engine surveys those blocks first.

Terrain. Ground is terrain, as in Second Life: square tiles TERRAIN_TILE_M on a side, aligned to multiples of TERRAIN_TILE_M, flat at z = 0 for now and given a heightmap Later. A tile is part of the world, not an object: nobody owns it, and it cannot be moved, taken or destroyed. The engine creates a tile when a surveyed plot first needs ground there. Tiles collide, carry navigation and are sent to viewers (S6.2). They are not saved: on loading, the engine rebuilds them from the plots. Outdoors, where no zone sets the ambient light, the ambient is the world setting base.outdoor_lux.

For a cell c of a lot, n(c) is the number of the port nearest the lot's center and a(c) = |x + 0.5 - n(c) * PORT_SPACING_M| is its distance from that port along the Street. For a cell of a lot that fronts the Street, its depth d(c) is the number of whole meters between c and the Street: 0 for a cell that touches the Street, 1 for the cell behind it, and so on.

### S13.2 Value

p(c) = exp(-a(c) / land_along) / (1 + land_port_falloff * |n(c)|)

v(c) = land_base + land_back * p(c)                                  if c's lot does not front the Street

v(c) = land_base + land_front * p(c) * exp(-d(c) / land_depth)         if it does

V(P) = the sum of v(c) over the cells of P

p(c) says how near a port a cell is. It is 1 at Port Zero and falls with distance along the Street, and a little with the port's number, because people arrive at ports and the monorail between ports is fast. The back of a deep Street lot is cheap, but still worth more than land the same distance back on a lot that does not front the Street. Extra depth adds less and less. There is no other premium or discount for size. The script computes V from a lot's bounds and computes it again when the bounds change, so a split or a join revalues the pieces.

Defaults: land_base = 1, land_front = 9 and land_back = 1, in money per square meter; land_along = 250 m; land_depth = 16 m; land_port_falloff = 0.01, so a lot at port 100 is worth about half as much as the same lot at Port Zero. A 16 m by 32 m Street lot next to Port Zero is then worth 2440.01, the back lot behind it 992.34, and the Street lot at the same place at port 100 1476.01.

### S13.3 Rent

The held value W(o) of a player o is the sum of V over the plots o owns. The tier charges the part of W beyond land_tier_value at a higher rate, as Second Life's tier does:

f(W) = W                                                            if W <= land_tier_value

f(W) = land_tier_value + land_tier_multiplier * (W - land_tier_value)   otherwise

rent per day of a plot P owned by o = land_rent_rate * V(P) * f(W(o)) / W(o)

The rents of all of o's plots add up to land_rent_rate * f(W(o)). Plots in the pool owe nothing. Defaults: land_rent_rate = 0.01 per day; land_tier_value = 5000, about two Street lots by Port Zero; land_tier_multiplier = 2.

Every base.settlement_seconds the script visits the owned lots in id order. A lot's debt grows by its rent per day times the days elapsed. The whole units of the debt are paid with engine.pay from the owner's wallet to root, p:0, under a spend grant the owner gave the script, and leave circulation; if the payment fails, the debt stays. When a lot's debt reaches 1 the script notes the time, and it clears the note when the debt falls below 1. When the debt has stayed at 1 or more for base.rent_grace_days, the script holds the owner's things on the lot, under root's grant on all land, and then abandons the lot to the pool, which returns everyone else's things (S9.2). Held things are salvaged after base.rent_hold_days, and their material goes to the script's stock.

When a lot changes owner, its debt starts again at 0. The new owner finds the rent per day in the script's posted writing, and pays only through a spend grant to the script. An owner who has not given that grant, or who revokes it, simply does not pay.

### S13.4 Selling pool lots

Pool lots fall into two classes: Street lots and back lots. The scarcity of a class is s = 1 - (the sum of V over its lots in the pool) / (the sum of V over all its lots), and its price factor is K = 1 + land_scarcity * s. Default: land_scarcity = 1.

At most land_on_offer pool lots of each class are on offer at once (default 2). Whenever fewer are on offer, the script offers the class's pool lot with the lowest id that is not yet on offer, to anyone, so the lots nearest Port Zero go first. A lot's age t is the number of days since that offer was made. A lot that comes back to the pool later is offered again with a new age.

start = land_start_multiple * V(P) * K

floor = V(P) * K

price = max(floor, start * 2^(-t / land_halving_days)), rounded up to a whole unit

Defaults: land_start_multiple = 3 and land_halving_days = 1, so a price reaches its floor in about 1.6 days. Every base.settlement_seconds the script sets each open offer's price to the current value. A buyer may buy from anywhere, naming the most they will pay (S9.4). The money goes to root and leaves circulation.

Rejected: fixed prices, because the fastest agent takes every underpriced plot; a lottery, because it ignores how much people want a plot; self-assessed prices with a standing duty to sell, because a forced sale of someone's home is hostile.

### S13.5 Money

Root's account has unlimited money and holds none (S1.7). Rent and pool land sales are paid to root and leave circulation. Money is created only by payments from root, under spend grants that root gives in the start file, each with a cap per period: one to the power purchase on the public circuit, and one to each architect, for building public things and buying land for them (Proposed: 1000000 per 7 days). The caps bound how fast money is created and what a compromised script or account can take.
