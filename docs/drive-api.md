# Single-writer scheduling and execution boundary

`server/drive` owns clock/budget bookkeeping, typed external-input rows and native-operation registrations. It coordinates the existing step, install, command and execution libraries. It does not own world tables and receives no universal context. Pure planning operations read their exact projections; event/watch/action execution use distinct local adapters. Main still allocates independent tables, wires each adapter and runs space/perception/replication/record/snapshot phases explicitly.

The alternatives are one runner class borrowing every world table, a virtual service graph, or a small scheduler with separate planning/execution functions and operation-local native callbacks. Use the third. A callback's reviewed context belongs only to that operation; no callback may capture main or an aggregate containing every adapter.

## Clock, queues and admission

`Clock` holds the current simulation step, next wall-clock boundary and overrun count. `PhaseCosts` is a configured-size ring (20 prototype samples) of the measured total cost of space, perception, replication, record and snapshot phases. `Frame` is a transient value: start, handler deadline, next boundary and background-item count. Settings explicitly supply STEP_HZ, STEP_MARGIN_MS and PHASE_AVERAGE_STEPS.

`begin_frame` raises the step, promotes due timers, then appends this boundary's arrived inputs after all prior queued work. Its handler deadline is frame start plus `max(0, period - recent_other_phase_mean - margin)`. The scheduler checks the deadline **before admitting a whole work item**. Once admitted, all of its broad-to-narrow handlers finish, each under the configured per-handler deadline, then the direct action/handler records and descendants are published. S2's foreach-handler loop has no inner admission cutoff. This avoids unsaved half-action drafts or withholding a chosen action's record across frames; a large dispatch can honestly overrun a frame.

Causal work always precedes the next external input. When the budget expires, queued descendants remain before external turns next frame. Background runs until the handler deadline, with at least one available item per step even when foreground consumed the budget. That explicit S2 fairness exception may run one background item while older causal work awaits the next frame; its own descendants append behind older causal work, and no new external input overtakes that queue. The scheduler never drops work because a frame is busy. Only emitted event/action overflow follows the existing EVENT_QUEUE_MAX policy; watches remain coalesced and nondroppable.

`finish_frame` records measured other-phase cost and returns the next wall-clock wake point. An overrun starts the next frame immediately and increments the overrun count; simulation still advances one fixed collision quantum per frame. It does not skip physics steps or execute an unbounded wall-clock catch-up burst.

To preserve S2 ordering for bake completions and structured native controls, append a plain `step::InputWork{uint64 input_id}` alternative to Work. `drive::Inputs` owns copied rows keyed by monotonic id: operation name, authenticated caller/body, session/sequence, request id, ordinary JSON fields and Origin. No credential, pointer or callback is stored. Root's S6 handler only enqueues this copied input and returns pending. Its actual operation runs when InputWork reaches the ordinary foreground lane; a completion callback may enqueue another session input but cannot mutate the world inline. Inputs and their id high-water mark join QUEU persistence. Script-origin `ActionWork` remains the existing typed ordinary action, with no player body. This avoids a second independent queue whose old inputs could accidentally be overtaken by newly due timers.

The actual phase loop takes individually supplied typed event/watch/action/input/background consumers. Each is a function pointer and its own reviewed local context. There is no `DriveContext` or shared Services object. Phase selection owns only queues, clock and budget, while the supplied consumer executes one admitted item synchronously. Tests also exercise pure `next`/admission functions with explicit times, avoiding flaky sleeps.

## Pure planning and real execution

`plan_event(Triggers, ValueRead, EventWork, step, hz)` reads current selector flags through the normal resolver, calls ordinary broad-to-narrow dispatch and returns copied invocation inputs. Events cannot inherit action caller/body/target or direct-body authority. Invalid target generations produce no handler plan. A promoted threshold token is checked against identity/process/subscription revisions, then becomes dirty work; its placeholder event is never dispatched directly.

The watch adapter has only subscriptions, typed WatchLinks and ValueRead for its mutation/read stage. It calls install's dependency refresh and current-answer comparison, then `plan_deliveries` with Triggers/Scripts/ValueRead. Root's execution stage consumes those plans using the existing narrow `bindings::Execution` (VM, script states, per-object RNG, identity and declared-parts relation). Invocation receiver remains the installed consumer; a followed source is acquired for reads. The adapter schedules returned threshold timers and queues returned rebound facts through the step APIs.

The background adapter validates a copied catch-up item against current generation, selector, active rule version and actual shared-row existence. It builds the same real invocation input, without a player authority envelope. Root synchronizes applicable rule watches before running a newly active catch-up. Restore reconstructs links/dispatch and resumes saved work; it does not manufacture new catch-up merely by restarting.

Structural outputs are applied immediately after each VM return through a registry keyed by StructuralRequest kind. Each entry is a typed operation function and its own context. Its returned completion contains actual direct changed, created handles, completed records and further typed outputs. The driver merges those values into CompletedInvocation, drains its structural list, then calls existing publish_invocation/publish_action. Allocation/initialization/cleanup still occur through separate narrow module calls in the root-owned structural implementation; the registry is not permission to introduce an all-table constructor callback. State already written by Luau stays on errors/cutoffs, with no rollback scope.

## Action pipeline and native controls

The resolver reads only native declaration metadata, Terms, Models, Scripts, instance installation, identity and an explicitly supplied authenticated player body. Root's input adapter keeps a raw JSON `native_args` value alongside the ordinary ActionRequest; only a reserved native operation receives it, and that operation validates its own structured metadata. Script actions decode to the shared flat EventPayload and are checked against the registered typed input signature. Unknown actions, stale handles, missing fields and wrong argument types finish with a readable result before any handler runs.

Permission preflight is a separate read-only operation over authority/identity projections, owner limits, Players and Grants. It maps the declared standard right to the corresponding permission verb and checks the resolved endpoint. Reach preflight receives only current transforms, actor/endpoint handles and the supplied reach distance. A player actor uses the authenticated body; a script actor uses its installed object and never acquires a player's body or owner shortcut. Native structured operations retain their own plot/account/grant/role checks; a generic dispatcher cannot authorize their specialized mutation by guessing from one object right.

After preflight, the action handler planner reads Triggers/ValueRead and the resolution. A body route executes on that body, with the selected handle as its second Luau argument. An ordinary object route uses the actual player's body as the second argument, or the installed object for a script caller. Immediate `action_caller`, `action_body` and `action_target` describe the actual input and are cleared for later event/timer/watch work. They are not wallet or physical authority. **Only** the handler whose script is the resolved body's declaration gets `direct_body{actor,body,selected,held,declared mechanics}`. Sibling material/model/instance handlers have ordinary script authority, even on the same body action. Script-origin actions always have an empty action_body and no direct_body.

Native operations are registered per action term as validator/function/operation-local context. They return a `NativeCompletion` value containing the actual result/changed flag, reply fields, completed records and deferred work. A native action is recorded directly as its caller's action, then its descendants are stamped/published; it does not become a fake script handler or extra chosen action. Permission denial records a denied action and runs no native/script handler. Script actions use existing execute, per-return structural application and publish_action so the action record precedes completed handlers and their descendants. Direct changed is limited to this dispatch's actual mutations, including structure and excluding the actor's own position; it does not wait for a whole causal chain.

The ordinary runner receives these stages separately: resolution, typed validation, permission, reach, planning, execution/structural completion and publication. Main wires their exact contexts. No stage gains native ledger/catalog/physics mutation merely because another native operation needs it.

## Public API and acceptance

The concrete headers will expose independent `Clock/PhaseCosts/Frame`, `Inputs/InputOperationRegistry`, `NativeActions` execution registration, pure `plan_event/plan_action/plan_background`, and permission/reach preflight functions. The phase functions receive distinct per-kind consumers, not a single callback borrowing every table. Input codecs take only Inputs and snap serializers. Production settings all come from config; test fixtures pass explicit values.

Tests must use the actual VM/execution driver for invented event/action/watch handlers and prove strict action-descendant-before-next-input order, shared watched-value coalescing, due/stale threshold behavior, catch-up filtering, one background item under an exhausted budget, actual per-handler errors/cutoffs, denied action suppression, body receiver versus permission endpoint, script-origin authority separation and action-first record order after structure. Pure clock tests verify recent-cost averaging, deadline admission and overrun progression. A scheduler callback probe establishes ordering only; it cannot replace the real Luau/action integration tests or full-world performance gates. Benchmark admitted real handlers, dense watches and event/input queue throughput separately from other-phase costs.
