# Action resolution boundary

`server/command` resolves and validates action requests. It owns the registry of reserved native action metadata, not the handlers' game tables. Resolution reads identity, model/script declarations and the instance installation column. It returns copied declaration metadata, its receiver and a permission endpoint. The runner obtains applicable handler references separately through reaction dispatch. Resolution neither runs Luau nor changes the world.

For a player, the authenticated adapter supplies that player's current body. A script caller has only its installed-script holder and supplies no player body. Reserved native administration resolves first; script submission must reject a declaration colliding with one of those registered IDs. For other actions, a matching body declaration resolves first, then a declaration on the selected object, then the selected object's material/flag/model/instance event dispatch with the ordinary use right. With no selected object, the body is the fallback receiver. No physical verb spelling selects a branch.

The script installation always determines the handler receiver. A body script runs on the body even while operating on a selected world object. Declaration `right_on` chooses `self` or `selected` as the endpoint for the declared permission/reach check; it never changes which object the script is installed on. The runner uses a Body resolution to create a direct-body envelope only for an authenticated immediate player invocation of that player's body declaration. It includes the actor, body, selected target, current held object and the declaration's mechanical operations. Event/timer/watch work and self.act never manufacture that envelope.

One action term has one typed input signature. Script inputs use the shared flat typed payload (scalar, handle, vector, string or registered term). Validation reports missing, unknown and incorrectly typed fields with the signature. Native administrative controls may validate their operation-specific JSON at their own adapter, because registry proposals and grants contain structured metadata rather than gameplay event records. Unknown term IDs, stale selected handles and an absent required selected endpoint fail before executing handlers.

The action runner is a separate adapter. It checks the resolved right and reach, obtains broad-to-narrow handlers, runs each VM invocation, applies that invocation's structural commands, and retains completed handler/effect drafts. It writes the completed action first, then completed handlers/creation records, and publishes their descendants with those Origins before taking the next external input. Module-owned state remains with the narrow VM bindings; resolution never gets properties, processes, physics, ledger, Journal or queues.

An alternative was one dispatcher that receives every table and implements every native action; that would recreate the rejected architecture. Another was a general service interface for all operations; that adds indirection without improving this small module. Plain resolution results and separately registered operation-specific handlers preserve the boundaries while keeping the hot path direct.

Tests resolve a newly named body verb, object action and world-rule fallback, distinguish handler receiver from permission endpoint, check instance declaration precedence and script caller identity, reject stale targets and validate typed arguments. Real VM/physical effects remain binding/integration tests; metadata tests do not establish playability.
