# Reproducible S11.5 Wikipedia acquisition

The frozen statistic remains Spearman correlation of weekly measure changes and changes in log summed 2024 pageviews, pooled across 40 worlds, with 1,000 whole-world bootstrap resamples. Acquisition does not inspect those outcomes to choose categories. The exact procedure was registered before the draw in `.cache/measure-wikipedia/acquisition-preregistration.json`.

The actual validation is complete: [the final report](../reports/wikipedia-validation-final-2026-11-15.json) measures all **40 worlds × 53 periods** from real histories. All twelve correlations are undefined with zero paired changes because [2,120 independently verified source obstructions](../reports/wikipedia-availability-final-2026-11-15.json) prevent defined weekly readership sums. The reader stopped at **18,540 cached / 30,022 uncollected articles**; annual readership acquisition remains explicitly incomplete. No unavailable value was fabricated from an uncollected page. The fixed sample and frozen formulas were not changed.

## Category sampling

The source is the complete [20261101 English category SQL table](https://dumps.wikimedia.org/enwiki/20261101/), 35,130,311 compressed bytes, official SHA-1 `4171324b173a1518ed4d8f05924781e36f301bd5`, actual SHA-256 `db001eaa0ab9cbcd16c6c01e4049d2b79254bfd73376650bce1483b62ad3fcf4`. All 2,653,947 rows enter the candidate universe, including empty and hidden categories. The imported immutable ordinal table sorts original category-title bytes. Invalid historical UTF-8 rows retain their bytes and remain in that universe.

`python3 -m measure.wiki_sample` draws uniformly without replacement with seed 20261115, by `Random(seed).randrange(1,N+1)` and duplicate rejection. It accepts the first 40 eligible categories. Rejecting ineligible candidates from a uniform permutation gives a uniform sample without replacement of eligible categories: each eligible relative order appears equally often in permutations of the complete universe. This avoids constructing an entire category graph. The 40 selections are **not an enumerated complete eligible frame**; its total size remains unknown.

An eligible tree has 500–5000 distinct nonredirect mainspace pages at root depth 0, child depth 1, or grandchild depth 2. Category cycles and repeated articles are deduplicated. All categorymember continuation pages are consumed before acceptance or a below-500 rejection. A more-than-5000 rejection retains the actual unique-page lower-bound certificate. A current leaf category with fewer than 500 noncategory/nonfile pages can be rejected from categoryinfo's upper bound. Categories are measured during the recorded API retrieval interval, which is not a frozen 2024 membership graph. Article IDs remain fixed for the 2024 history analysis. Associated uncategorized talk pages are not added.

The first run stopped at an old SQL title containing Unicode whitespace: the API normalized it to another title. The correction rejects such noncanonical stale titles with the recorded normalization response, rather than sampling an alias as a second category identity. Invalid UTF-8 titles similarly have an explicit byte-preserving rejection. This source-identity clarification is recorded separately in `acquisition-clarifications.json`; the original registration and outcomes remain unchanged. Resuming replays the same ordinal prefix and cached decisions.

Alternatives considered were exhaustive reconstruction from roughly 6.5GB of SQL tables, and sampling an API search/popular-category subset. The former adds a large graph without improving this rejection draw; the latter cannot provide uniform coverage. The complete pinned universe and recorded rejection decisions are the chosen method. Every draw, decision, accepted article set, traversed category/depth, and response proof is retained in `draws.jsonl`, `selected.json`, and `api-cache/`.

`python3 -m measure.wiki_study verify` independently replays the exact ordinal prefix and every eligibility certificate from raw cached bodies. It validates original dump/checksums, database hash, response URL/body hashes, closure continuations, accepted IDs/titles, and the first-40 stopping rule. Missing or altered evidence fails; it never requests replacement responses from the network. `sample-proof.json` reports the checked response count and actual membership retrieval interval.

## API rate and durability

The [Action API etiquette](https://www.mediawiki.org/wiki/API:Etiquette) recommends serial requests, batching, caching, and noninteractive maxlag. The [current rate policy](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits) lists 200 requests/minute for identified unauthenticated clients. The [Analytics API access policy](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/documentation/access-policy.html) links the same policy. All API stages run serially, including one stage finishing before the next starts. The client uses `maxlag=5`, a descriptive user agent, exact cached bodies with SHA-256 proofs, and Retry-After/backoff handling.

The initial implementation slept 0.35s after each round trip: 114 actual requests took 61.7s. The revised persistent HTTPS client uses a minimum 0.35s between request starts, at most about 171 requests/minute. Two actual Analytics requests took 0.136s and 0.126s in one persistent connection. This reduces repeated TLS overhead without adding parallel requests or exceeding the aggregate limit. Neither privileged bot limits nor private Wikimedia access are assumed.

## Histories and readership

All 12 monthly 2024 files from the [official MediaWiki history 2026-10 snapshot](https://dumps.wikimedia.org/other/mediawiki_history/2026-10/enwiki/) were downloaded, totaling 7,432,569,766 compressed bytes. [Each snapshot reconstructs the full history](https://dumps.wikimedia.org/other/mediawiki_history/readme.html); the 2024 events in this coherent snapshot are valid historical inputs. Mixing monthly snapshots would be inappropriate. The downloader records URLs, sizes, SHA-256 checksums, and validator-bound resume metadata. Filtering retains the original 78-field TSV serializer rows, including `revision_text_sha1`. Page IDs, event user IDs, and first-edit timestamps come from the records. Missing maker metadata uses the frozen first-event inference; no lifetime-first-revision request is required merely to fill an optional field.

The [per-article Analytics API](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html) supplies 2024 daily all-access/user counts. Its identity is title-based; [Wikimedia's analysis notes](https://meta.wikimedia.org/wiki/User:Isaac_(WMF)/Analysis_gotchas#Page_Moves) explain why querying current titles alone loses moved-page history. The collector batches current page metadata and downloads the complete public move log from 2024 through a fixed metadata cutoff. A move's `logpage` identifies the moved article; `pageid` may identify the created redirect. Reversing the verified chain yields each page's canonical title intervals. Deleted pages and incoherent public move chains are unavailable, with diagnostics.

A daily count cannot be apportioned honestly across a midday title move, so that page-day is unavailable. Deleted pages and incoherent title chains are also unavailable. The collector retains the original responses, including omitted daily items and HTTP 404 evidence. The final offline projection applies the same source decoder as collection, then applies stable-ID existence bounds. Old provisional per-page caches remain unchanged and are independently hashed; replay uses their actual API bodies rather than their earlier inferred values.

### Published zeros and source limits

The [official troubleshooting contract](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/documentation/troubleshooting.html) says zero values are omitted and a 404 can mean zero views or data not yet loaded. Its [comparison tutorial](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/tutorials/compare-page-metrics.html) fills omitted entries with zero. These queries concern mature 2024 data, rather than the ordinary recent loading interval. Therefore successful omitted items and cached 404 responses decode to **published zero**, with their original omission/status metadata retained. Actual request failures and malformed responses never become zero. Known suppression remains unavailable: the pinned official Cassandra exclusion list, SHA-256 `fa0e7cfae5014a1e2585fed69e01577845a9f7b7c52b84c9b3a65cce3bd7095b`, matches none of the selected historical titles. Historical changes to that list remain a source caveat.

This corrects the earlier blanket omitted-item→NA interpretation, which was stronger than the source contract. That initial interpretation and its raw missingness audits remain evidence, not a frozen S11 definition. The [documented 2024 data incident](https://wikitech.wikimedia.org/wiki/Data_Platform/Data_Lake/Data_Issues/2024-10-10_Webrequest_Data_Loss_-_Clobbered_Hadoop_Temporary_Dir) affected approximately 0.2% of upstream data before September 9 and was later backfilled with downstream reruns, resolving October 18. Published positive counts can also reflect source undercoverage; treating every omitted item as unloaded would not fix it. The reviewed primary sources identify no unresolved whole-day 2024 loading gap. The study measures published counts and retains those limitations, rather than claiming a perfect census.

### Source creation and existence evidence

A complete positive title series can partly belong to a predecessor or redlink. In the actual selected move chains, fourteen IDs share a backwards-filled `User:SimonLagann/sandbox` title; three have source creation dates in March or May 2024. The risk does not depend on a series having missing items. A regression therefore exercises a complete positive annual series as well as historical cache values previously inferred as zero.

`build_creation_records` projects the verified twelve histories' `page_creation_timestamp` values, keeping all distinct dates and first-edit diagnostics. A cached creation log is accepted only when its `logpage` matches the selected ID. **Creation establishes existence by that instant, not absence beforehand.** The first interpretation as lifetime birth was falsified by nine actual positive January 1 ID/title observations preceding a later source creation timestamp: examples include J. D. Vance, Bloodlands and Hollow Knight: Silksong. Restoration and merging can preserve an earlier identity. The [official schema](https://wikitech.wikimedia.org/wiki/Data_Platform/Data_Lake/Edits/Mediawiki_page_history) and [source reconstruction discussion](https://phabricator.wikimedia.org/T220507) distinguish creation and earliest edit; neither an imported old revision nor numeric page-ID order is promoted to an unverified existence proof.

The actual source projection covers all 48,562 selected IDs: **39,529 have one consistent creation value, 9,033 have none, zero have multiple distinct values**. Of those without a known value, 9,032 have no 2024 source rows. Six rows have null creation timestamps and no timestamp parse failed. The single-valued dates comprise 38,175 before 2024, 1,341 during it and thirteen after it; 515 pages have an earlier first-edit value. Those are source diagnostics, not lifetime-birth classifications. Historical edits and the frozen adapter's creation metadata remain unchanged. Current source evidence is `study/page-creations.json`, SHA-256 `d684cbfe4a546677c50829c6c342055b319a917380e6731be1f747ee70662a7b`; the initial birth-named evidence files remain preserved separately.

The retained January 1 official user dump supplies another conservative witness: a positive row must match both the selected ID and its coherent historical canonical title. The [official pageview schema](https://wikitech.wikimedia.org/wiki/Analytics/Data/Pageview_hourly) obtains IDs from contemporaneous X-Analytics headers and warns that redirects may carry redirect or target IDs. Aliases, null IDs and absence therefore supply no witness. An exact match proves existence by January 2; it establishes neither an identity-pure January 1 total nor any earlier absence. This recovers **3,444** IDs without a known history creation value and records the nine observations preceding source creation; **5,589** IDs remain without either source of evidence. The current witness file is `study/page-existence-bounds.json`, SHA-256 `e3578218c9f06329a3a9472499a5a4007079e0a3240eed525857333e59c0c964`. Bulk values never replace AQS counts.

For a positive daily title count, the earliest supported existence cutoff must cover the start of that day; otherwise that page-day is NA. A published zero can enter zero without an existence witness: it attributes no positive predecessor traffic and asserts no absence. Unknown, moved or suppressed title days remain NA. Multiple creation records and earlier observations remain diagnostics; they are not reasons to discard an independently verified later day. Original bodies, provisional projections and failed interpretations are preserved, while final corrected records receive separate provenance hashes. [The policy report](../reports/wikipedia-identity-policy-2026-11-15.json) records this decision before any primary correlation was inspected.

The sole serial reader was restarted to prioritize the unchanged selected worlds 1411443, 2189472 and 444539, whose coverage was not already blocked in every week by cached positive-identity or move evidence. Their 2,163 distinct articles included 1,875 uncached IDs at restart. This changed request order, not the fixed forty-world sample or any statistic. After a shared-policy audit found every week of the first two worlds already obstructed, a second serial restart prioritized only world 444539. The reader was then stopped at 18,540 cached articles, leaving 30,022 uncollected. The final certificate independently verifies every one of the 2,120 weekly obstructions against 92 actual page IDs and their original positive AQS response bodies. Complete annual readership acquisition is not claimed. Progress `requests` counts successful responses only; HTTP errors, 404s and retries are separately cached and paced but excluded from that counter. The old/new process boundary is recorded in [the restart report](../reports/wikipedia-reader-restart-2026-11-15.json).

The [pageview_complete bulk alternative](https://dumps.wikimedia.org/other/pageview_complete/readme.html) has page IDs and daily/hourly counts, but daily user files around 0.5GB imply roughly 200GB for 2024 across all projects, exceeding the 59GiB initially free if retained whole. A streaming projection remains possible, but would require a measured schema/throughput and handling missing page IDs/access methods. It is not substituted for the declared article-view definition. The actual sampled article and distinct-title workloads were recorded in the preserved acquisition logs. At the permitted serial rate, tens of thousands of article requests take several hours.

### Measured bulk alternative, 2026-11-15

A separate read-only check fetched the twelve static indexes and exactly one daily user dump; it made no API requests and changed neither the study nor the running reader. The indexes contain all 366 daily files, totaling 205,684,818,175 compressed bytes. The complete 2024-01-01 file is 485,967,461 bytes, downloaded in 99.676 seconds and verified through bzip EOF; its SHA-256 is `44a8b02ee71555e90b14f7faaa13a6b14b448b4f367e01f2dca35cd6e919b463`. Evidence and the bounded projection scripts are linked from [the feasibility report](../reports/wikipedia-bulk-feasibility-2026-11-15.json).

The [actual generation SQL](https://gerrit.wikimedia.org/r/plugins/gitiles/analytics/refinery/+/refs/heads/master/hql/pageview/daily/make_hourly_dumps.hql) groups user traffic by project, requested title, page ID and access method, then sorts by project/title. Its space-separated CSV requires quote/escape decoding. Summing the three access methods for the historical requested title reproduced all 7,833 already cached AQS counts checked for 2024-01-01. Joining only on ID reproduced 2,622: every mobile-app row lacks an ID, other access methods also have null IDs, and redirect aliases can share an ID. That day has 9,882,045 English views without IDs, of 280,418,461 total. ID availability does not remove the study's existing title-interval or move-day exclusions.

User-only bulk also cannot distinguish an absent title from an explicit AQS zero. The cached comparison includes 306 explicit zero counts; the [AQS loader](https://gerrit.wikimedia.org/r/plugins/gitiles/analytics/refinery/+/refs/heads/master/hql/cassandra/daily/load_cassandra_pageview_per_article_daily.hql) can write zero user views when another agent type supplies the title's row, and applies a disallowed-title filter absent from bulk generation. Its current disallowed list matches none of the selected lineages; this does not verify historical filtering or all-year equivalence. Missing bulk titles must not silently become known study zeros.

The measured Python full projection took 166.707 seconds for 2.677GB of decoded data. Stopping after the complete sorted English prefix read 224,395,264 compressed bytes and took 108.306 seconds. Scaling this one day's throughput and project mix by the actual annual compressed size gives 11.72 hours of full-file transfer and 19.60 hours of Python projection; prefix transfer is an optimistic 5.41 hours, with 12.73 hours of observed Python projection. These are extrapolations on a shared host, not measured year-wide or parallel performance. The serial collector then had 8,400 of 48,562 pages complete, about 6.50 hours remaining at its observed 103 pages/minute. That was the measured estimate before the later existence audit established the early stopping condition. An optimized parallel bulk implementation was not substituted; its speed and exact identity/missingness equivalence were not established.

## Reproduction and missing data

The stored actual study can be reproduced without any new API request:

```sh
python3 -m measure.wiki_study assemble --certified-unavailable \
  --existence-bulk .cache/measure-wikipedia/bulk-feasibility/pageviews-20240101-user.bz2
python3 bake/run.py -m measure.validate \
  --input .cache/measure-wikipedia/study/study-input.json \
  --output measure/results/wikipedia-final
```

The assembler independently replays the complete-universe draw and all twelve verified history projections, rebuilds creation/existence evidence, and recomputes the actual cache-based weekly certificate. The certified mode rejects any world-week that is merely uncollected or actually available. It accepts only an actual source obstruction in every week, and writes `readership.complete=false` with the certificate hash and exact cached/uncollected counts. An unknown term already makes a sum undefined regardless of the remaining terms; this mode does not fabricate their values or remove sampled articles. The full-acquisition mode remains available without `--certified-unavailable` and requires the normal complete-readership marker.

The source acquisition entrypoints are `measure.wiki_sample`, `measure.wiki_history fetch`, `measure.wiki_history filter` and the serial `measure.wiki_views` collector. Their exact original invocations, the later priority-only ordering changes and stop boundaries are retained in the report/logs. The downloaded January 1 witness file is pinned to its complete compressed SHA-256; it is not a full-year bulk download. The `measure.wiki_study histories` stage and `measure.validate --history-only` can separately reproduce the forty actual history-measure reports without any readership or correlation inference.

The final assembler returned success in 167.834 seconds. Unchanged `measure.validate` returned success in 29.956 seconds and retained all forty worlds and their 2,120 period reports. The validation output SHA-256 is `4d3022ef453a1fd44025e5ad85b03f85a06e64d1262864fbbd9258769d08f670`; the study input is `84121d693fd2a53770924773a2af4e408dfbc90fdf55348a292dec9a5e6a5aa5`; the final certificate is `383564bee7b1d9cec373b9a19c0661eae29ebe9d691baeae965b8e3419227118`. All twelve coefficients have zero paired changes and are undefined. The frozen routine configured 1,000 whole-world resamples but attempted zero because no point statistic was defined. There is no artificial coefficient or confidence interval.

Any genuinely unavailable article-day makes its summed world-day and containing week unavailable. Weekly logarithmic changes require two positive known sums. Published omitted zeros follow the official mature-data contract; no pseudocount or changed sample fills identity gaps. A future defined comparison requires additional dated stable-ID/title witnesses or authoritative lifecycle evidence for unresolved positive days, then acquisition/audit of the remaining counts. The 92 actual certificate pages are witnesses to the present failure, not a guarantee that only those identities need further evidence. More title counts alone cannot repair an already unresolved positive identity term.

The public dump and APIs are reachable. An initial default-urllib 403 was resolved with proper client identification; it is not an external-access blocker. The actual unavailable correlations are explained by verified positive-identity ambiguities with preserved source evidence, rather than unreachable data or inputs merely not supplied.
