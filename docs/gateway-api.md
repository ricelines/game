# Agent gateway and authoring adapter contract

This is the boundary between the Python gateway/harness and the native modular monolith. It contains no Python gameplay policy. The server authorizes, observes, executes actions, compiles scripts, and registers models at step boundaries. The gateway manages player sessions, presentation of observations/events, queued authoring jobs and model calls.

## Five tools and player sessions

The MCP and CLI expose exactly S5 `look(limit?, full?, events_limit?)`, `inspect(target, events_limit?)`, `actions(target?, name?, page?, events_limit?)`, `do(action,target?,args?,events_limit?)`, and `cancel(events_limit?)`. `events_limit` is an envelope option, not a new gameplay action. Results are the same JSON, including `events` oldest first and `events_omitted`. The default shows the newest 40 pending events; requesting a larger limit exposes more. Inspect accepts handles or `self`, `inventory`, `grants`, `plot` unchanged. No browser world-action endpoint is introduced.

Each logical gateway session has one native `/ws` connection and sends S6 `hello` with mode `play`, binary false, and its player key. A second independently opened session replaces the first at the native server. CLI invocations share the gateway session identified by an explicit `X-Ambergris-Session` token, default `cli` per player key; a harness owns a separate explicit token. This is application state, independent of stateless MCP transport. The gateway never invents a player identity from a requested handle. A closed/replaced native connection starts a new native observation baseline. Requests on one session serialize in arrival order.

For native controls use the exact original S6 messages:

```json
{"t":"hello","version":1,"key":"PLAYER_KEY","mode":"play","binary":false}
{"t":"look","id":1,"limit":40}
{"t":"inspect","id":2,"target":"self"}
{"t":"actions","id":3,"target":"o:17.1","name":"author.action","page":0}
{"t":"do","id":4,"action":"author.action","target":"o:17.1","args":{}}
{"t":"cancel","id":5}
```

Replies preserve the request id and are `obs` for look, `result` for do/cancel and `inspection`/`actions` for those queries. The gateway also accepts a `result` envelope for a query. It removes transport fields `t` and `id` before returning S5 JSON. S6 pushed `event` messages queue until a tool response; a `bye` produces a precise disconnected/replaced error. Events never become a scripted fallback response.

The native session sends full descriptions for changed records and `{h,dist_m,bearing}` for unchanged ones. It also owns body/player action-list baselines. The gateway passes those rows and lists unchanged; it keeps no second description cache and never reconstructs missing fields. `look(full:true)` clears only the native sent-description/action baseline before encoding current perception. The CLI exposes `amb look --full`. A resident requests this on its first observation and whenever its transcript is reset, so a fresh model context receives current complete descriptions/actions. This does not clear acquired handles, alter perception/world state, or widen range, lighting or permissions.

Every listed action includes a one-line signature, for example `author.weigh(amount: number [kg], note?: string)`. Observation and inspection action arrays contain these strings; the richer `actions` records retain the callable `name` separately and expose the same `signature`. `?` marks an optional input, brackets contain the registered quantity's SI unit, and native structured inputs use their advertised JSON-schema types. The formatter reads declarations rather than recognizing action names. A malformed call to a known action returns `error:"bad_input"`, its `signature`, and a concrete `problem`; an unknown action cannot supply a signature. Accepted authenticated action requests with an unknown action, malformed target or incorrectly typed argument produce one chosen, denied, unchanged Action record retaining the raw action name, arguments and target. Malformed transport or envelope messages rejected before enqueue remain outside S7. Typed action validation and denials continue through the normal recorded action path.

## Current stateless MCP HTTP

Implement the current `2026-07-28` revision, JSON-response Streamable HTTP at `POST /mcp`, rather than the old initialize/session-header/SSE handshake. Every request includes `MCP-Protocol-Version: 2026-07-28`, `Mcp-Method`, and `Mcp-Name` for tools/call, matching JSON body fields. Clients advertise both JSON and SSE; this implementation chooses JSON responses. Required params `_meta` includes `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientInfo`, and `io.modelcontextprotocol/clientCapabilities`. Methods: `server/discover`, `ping`, `tools/list`, `tools/call`; unsupported methods return -32601. GET/DELETE return 405 because this server offers no independent event subscription. Tool results carry `resultType:"complete"`, `structuredContent` with S5 JSON, a matching text content JSON block and `isError` for execution errors. Gameplay denial remains normal structured result.

This choice follows the [official current transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), and [lifecycle](https://modelcontextprotocol.io/specification/2026-07-28/basic/lifecycle). Origins are checked against configured local/browser origins, bearer player keys authenticate requests, and the default listener binds loopback. MCP itself retains no connection session; the explicitly named game session above is required by S5.

Alternative: pin 2025-11-25 and implement initialize plus the historical headers. That is useful for older clients but adds a compatibility path and is not the current protocol. We recommend one current revision for this new prototype and explicit unsupported-version errors.

## Model bake and script upload

HTTP uses bearer player keys. `POST /bake/models` takes S8 `{source,params?,material?,text:{name,description,writing?}}` and returns 202 `{job}`. It schedules the existing sandboxed BakePool outside the session’s world-mutation lane. Ordinary actions, observations and unrelated authoring remain usable during CAD execution. Completed native registrations acquire the session’s ordinary ordered mutation lane; submitting a bake reserves no world position or authority. `GET /bake/jobs/ID` returns queued/baking/registering/done/failed, then `model`, `hash`, `measured` or `errors`. A strict-host sandbox failure is a failed job with its real reason; never execute unsandboxed.

The gateway submits a completed immutable artifact to the native adapter, on the same authenticated session, as:

```json
{"t":"register_model","id":10,"job":"JOB","asset":"SHA256","canonical_params":"{\"height\":0.1}","material":"base.material","text":{"name":"...","description":"..."},"manifest":{},"variants":[{"asset":"SHA256","canonical_params":"{\"height\":0.2}","manifest":{}}]}
```

`canonical_params` is the exact canonical JSON string used by bake.parameters to compute the source+parameter hash; native code must not reserialize numeric values to reconstruct it. `manifest` is exactly the published bake manifest. Optional `variants` carries the additional ready parameter sets from one definition-edit submission, each with the same source and a distinct canonical parameter set. The worker verifies every actual root/part artifact before writer installation; transported manifests are inspectable copies, not trusted measurements. Geometry preparation covers the whole batch. Existing catalog helpers preflight the complete family in fresh proposal-only scratch tables before allocating live model/parameter identities. The authenticated input supplies the author and original causal origin, and the complete batch produces one chosen registration record and receipt. Explicit `register_variant` remains its own chosen request. The native loader replies:

```json
{"t":"result","id":10,"ok":true,"model":"m:210","hash":"SHA256","measured":{},"variants":[{"params":12,"hash":"SHA256","measured":{}}],"record_id":123}
```

Ordinary model registration does not place world objects and never claims construction authority. Authored approved rules create ordinary objects through existing host structural operations. A duplicate source/params asset still creates a separate model per submission.

Native authoring completions return their actual S7 `record_id`, including denied registrations. A failed accepted CAD job must also appear as a chosen building attempt when no native registration record exists. The gateway sends `{t:"authoring_failed",id,job,operation,source_hash,errors}` through its authenticated session's mutation lane; `operation` is `model`, `variant` or `edit_model`. The native helper publishes a denied, unchanged record attributed to that authenticated player, returns its `record_id`, and allocates no model/script identity. Gateway registration errors retain existing receipts, so a worker/registration failure already recorded by native code is not published again. A job reaches final `failed` status after this publication completes, or exposes `record_error` if the actual connection could not record it. This is journal publication, not a pending world transaction or a geometry fallback.

`POST /bake/variants {model:"m:N",params:{...}}` inspects that model’s current verified `source`, `source_hash`, exact default `canonical_params`, and current-source `variants[]`. It bakes those requested values from the original source, then submits `{t:"register_variant",model,expected_source_hash,asset,canonical_params,manifest}`. Native code rechecks source identity and returns `{ok,model,params,hash,measured}`. The resulting ready parameter block changes no instance; applying it still uses ordinary authored actions and resources. A stale current source fails rather than registering a variant against a different definition.

`POST /bake/edits {model:"m:N",source:"..."}` stages a definition edit. It resolves the replacement source defaults for block0 and preserves explicit current variant values, filling newly added parameters from the new defaults. The bake subsystem's literal PARAMS resolver deduplicates those effective sets before each is baked once; removed or out-of-range required values fail. It then sends one ordinary proposed-model registration containing all ready variants, so automatic staging does not turn one edit submission into several chosen events. Every required CAD execution must succeed before proposal registration. The completed job returns `{status:"done",effect:"revision_staged",model,revision_model,expected_source_hash,record_id,variants}`. It never applies the edit automatically. The actual model author may invoke the available authored revision action, whose approved rule computes the aggregate material exchange before native atomic rebinding. New parameter sets introduced while a bake runs can make a proposal incomplete; application then fails and requests a fresh rebake.

CLI equivalents are `amb variant m:N --params '{"width":2}' --wait` and `amb edit-model m:N source.py --wait`. Existing `amb submit model source.py --wait` still creates a distinct ordinary model. All three commands poll through `registering`, and `done` is reported only after actual native registration. The resident’s corresponding authoring functions are `submit_variant` and `edit_model`; the five MCP game tools remain unchanged.

`POST /bake/scripts {source}` sends `{t:"register_script",id,source}` to the same native session. The native compiler/react adapter owns Luau AST validation and the concrete ABI declarations; the gateway does not infer approval from a hash or regex. Reply `{t:"result",id,ok:true,script:"s:44",hash}` or `{ok:false,errors:[...]}`, mapped to HTTP 200 or 422. The adapter derives author from session and records immutable source/hash/compiled declarations. It must return validation errors if compilation is not wired; do not pretend upload succeeded.

An alternative is a trusted local completion pipe. That avoids a control extension but creates a second request-correlation/auth channel. We recommend these authenticated generic controls over the existing session, with the server restricting authoring capabilities normally. No model/name/seed-specific controls are required.

## Real model harness and purpose UI

Resident definitions store `key_file` paths, never inline keys. Paths resolve from the launcher working directory and must refer to mode-0600 files. Native launch creates those files without printing their data and persists only key hashes in PLYR. The gateway reads them solely to authenticate its ordinary play connections. Public resident status omits both keys and file paths. Example nonsecret content fields are `{id:"p:2",name:"Mira",key_file:".runtime/keys/mira.key",purpose:"...",persona:"...",model:"gpt-5.4-mini",interval_s:8}`.

Optional `--resident-report PATH` atomically checkpoints model/tool evidence after every actual response and tool output: actual response IDs, latency/token usage and each resident's public identity/purpose/status plus Responses tool-call/output transcripts. When a conversation exceeds its context budget, reporting retains that completed context in `archived_transcripts` and records `context_resets`; the next active transcript requests native full observations. Each initial observation is checkpointed before the model call, with receipts recording native step, requested full flag, full/short row counts and presence of body/player action lists. Reporting explicitly omits credentials and key-file paths. A process interrupted during a call retains the preceding checkpoint, rather than depending on clean shutdown. This is separate from the native S7 world event record; it establishes which actual model output caused the observed actions. A bounded turn supports up to 12 successive model/tool rounds before the resident's configured interval.

Use `amb --key-file .runtime/keys/PLAYER.key look` for CLI authentication and `gateway.service --purpose-token-file .runtime/keys/WATCH.key` for purpose UI access. The launcher supplies actual paths. There is no implicit player or purpose credential. Explicit `--key` / `--purpose-token` and injected environment credentials remain supported for callers that already manage them.

A resident has content-authored identity/purpose/persona, an ordinary player key, a body from welcome, a model id and a bounded turn schedule. Harness decisions come from actual OpenAI Responses API output. The model sees the five game tools plus authoring submit/status function tools (not additional MCP game tools). It can author arbitrary build123d Python and Luau through those endpoints. Tool calls execute in emitted order per session and results re-enter the actual model conversation. No keyword match or prewritten plan generates gameplay. Model/API errors set explicit unavailable/error status and leave the world running.

`GET /api/agents -> {agents:[{id,name,body,purpose,status,model}]}` reads harness status. The server-provided agent_gateway origin selects the purpose service; a configured watch/purpose credential authorizes browser writes without exposing player keys in public metadata. `POST /api/purpose {agent,purpose}` changes the named resident's next model instruction and cancels its pending body intent through the regular cancel tool when needed. It does not perform the human's requested world action directly. Bind the spectator interface to this port only; bearer/allowed-origin configuration protects remote deployments. Missing credentials disable actual harness start with a clear error, never activate a local policy.

Model calls follow the [official function-call loop](https://developers.openai.com/api/docs/guides/function-calling): preserve model outputs, execute function_call records, return JSON strings in function_call_output with original call_id. Use the configured model's supported Responses function-call interface. Credentials are injected only by the authorized `with-openai-key` process wrapper and are never included in logs or source. Model selection is explicit configuration; test evidence names the actual model and response IDs, with token/latency/cost accounting where available.
