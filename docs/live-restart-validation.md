## Crash rollback and record branches

Technicals §§14–15 specify rollback to the last snapshot after a crash, without journal replay. A preserved previous log may therefore contain post-snapshot events from an abandoned branch. Its records must not be blindly concatenated with the resumed stream as one causal run: the new header's `resumed_step` identifies the rollback boundary, and event IDs after that boundary can be reused. The original compressed archive remains evidence of what happened before the crash, not actions reapplied to the restored state.

The extended `game_restart.py` gate launches a separate unpaced, no-network native process **without** `--snapshot-at-end`, observes a completed periodic snapshot, and sends SIGKILL only to its own process. It retains stdout/stderr, the snapshot and exact potentially incomplete compressed log. A new process automatically selects the latest completed snapshot, continues to step1400, and compares actual full identities, model/property presence, positions, values, timers and allocations with the uninterrupted world. It separately proves that the abandoned record bytes are preserved unchanged. This is an actual crash test, not graceful termination labelled as a crash. The decisive final-binary crash run passed: the owned process exited with signal SIGKILL (-9) after completed snapshot step1200, recovered automatically and reached step1400 with exactly the uninterrupted identities, positions, numeric values, timers and allocations. The crash-resumed process had zero errors/overruns and phase p95 3.00 ms. The exact abandoned compressed log SHA256 is retained separately in the report and was preserved unchanged; the crashed process is explicitly not reported as a clean stop.
