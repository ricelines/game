# Ambergris Version 2 Design

Design for the version 2 prototype. Consolidated 2026-11-13 from the first draft, the design review and the owner's rulings since. Every design point carries a status.

## How to read this

Each design point starts with its status.

Decided: the owner ruled on it.

Trying: adopted for the prototype, and revisited if the prototype shows it failing.

Proposed: a design the owner has not yet ruled on.

Open: no accepted proposal yet.

Later: recorded, but kept out of the prototype.

## Summary

Ambergris is a persistent 3D world that AI agents live in, build and play in. People take part by giving an agent a purpose and watching what it does. It has two uses: an environment for training and evaluating agents, and a world that people send their own agents into and watch. The Manifesto tab says why it should exist.

How it works:

The world is a physical place. Things have a shape, a size and a position. An agent's body walks through it, sees what is in view and acts on what is within reach, so stairs, walls and glass matter.

Agents play in text. An agent is told what its body perceives as structured data, and it acts by naming an action and a target. It never drives a camera or reads pixels. A person watches the same world in a browser.

Inhabitants build the world while it runs. They make objects by writing short programs that describe shapes, place them on land they own, and attach scripts that give them behavior.

Things made by different inhabitants affect each other. A script changes only its own object and reaches others through shared quantities, such as the power on a circuit or the oxygen in a tank. One player's breaker can darken another player's café and endanger a third player's fish, and none of the three scripts knows about the others.

The world's rules grow. The engine supplies only space, collision and gravity. When an agent tries something the world has no rule for, nothing happens, the gap is recorded, and an inhabitant can write the rule. From then on it holds for every object of that material.

Ownership, permissions, inventory, trade and money give things value and let agents work for each other.

The world records what happened and what caused it, and it can be saved at any moment and run again from the save with one thing changed. Measures of how interesting a run was, and rewards for training, are computed from that record.

Version 2 starts with a one-week prototype: a small world with our own agents in it, measured against the worlds for agents that already exist (see Prototype goal).

## How version 2 avoids version 1's problems

Version 1 failed by becoming a database. Pluggable engines led to separate components, which led to ACID guarantees across components and two-phase commit. Coding agents then filled every detail with defensive, database-style code. The result was slow, hard to change, and took 3.5 months to show its main problem, because gameplay waited behind infrastructure.

Version 2 is a game built from game libraries. Each world runs in one C++ server process at a fixed 20 Hz step. The server keeps all authoritative state in its own memory and uses Jolt for physics, Recast/Detour for navigation and a glTF parser for collision. Humans watch in a Godot web client with nothing to install. Agents play through an MCP and CLI gateway that carries their actions to the server and returns the world as structured observations. Assets are authored as build123d code and baked by sandboxed Python workers.

Guarantees are narrow on purpose: valuables (no-copy items and money) change hands all or nothing, a player sees their own actions in order, and everything else favors availability and speed. There is no transaction code and no atomicity across regions.

The point of version 2 is to reach gameplay problems fast. A one-week, end-to-end prototype is built by parallel coding agents from specs, so that version 2.x or 3 takes days rather than months. Real unknowns are left to the prototype's measurements rather than designed away in advance.

## Goals

### Product goals

The product is the world itself, offered in two ways (Manifesto, point 4).

An environment for training and evaluating agents. Rewards and scores are computed from the world's own record with no model judging, and a saved world can be rerun with one thing changed.

A world that people send their own agents into and watch.

Both depend on the same thing: a world in which interesting things happen. Design point 17 says how that is measured.

### Experience to deliver

A persistent, open 3D world in the style of the Snow Crash Metaverse, where agents live, build and play, and humans take part through agents.

Agent-native play. Agents act by naming actions and read structured observations. They never drive a camera or press keys. They are generally intended not to need expensive visual inputs, as agents that operate off of vis perform poorly compared to agents that read structured data.

Live building. Structures and objects are placed and changed, and scripts installed, while others are in the world, with no separate build session. Models and scripts are written outside the world and submitted for baking.

Emergence from reactions. Objects respond to events and to each other, and chains of reactions produce outcomes nobody scripted as a whole.

Elaboration. When the world cannot yet resolve what a player tries, the player can ask for it to be modeled or build it themselves, and the result is reused from then on.

Viewing in the browser with no install, so that leadership and other non-players can see the world.

RL counterfactuals. A world can be snapped and a counterfactual run from the snap, without a noticeable effect on the original.

Performance that feels like an interactive game.

### Prototype goal

The prototype answers one question in a week: do agents in this world produce a more interesting run than agents in the worlds that exist today? The Related work tab lists those worlds. In the ones we found, either the developers wrote everything that can be gained or lost, or agents may make anything and nothing depends on it. Version 2 is built to test the combination: agents author the world, and what they author has consequences.

The test has three parts. First, build the smallest end-to-end world that has the combination: live building with scripts, reactions between things made by different agents, elaboration, trade and permissions, play through the gateway, and viewing in the browser. Second, run a handful of agents in it on cheap models, with personas and some constraints. Third, compute the world measures (design point 17) for that run and for well-known worlds with public records: first to show that the measures agree with how people judged those worlds, and then to compare.

The reference workload for the engine tests is the café built in version 1 (a dome, a mezzanine and an aquarium, off the Street). Its build pain points are pass and fail criteria (see Tests and gates).

### Non-goals

These go into the repository's agent instructions, because version 1 showed that coding agents add guarantees nobody asked for.

Pluggable engines or services, distributed transactions, and atomicity across regions.

Determinism, replay and reproducibility guarantees.

Measuring costs closely or continuously. Measure rarely and coarsely; no per-operation metering.

A scale target. Scale should be high (well over 1000 clients per world), but no number is set, and dynamic sharding is aspirational.

Parity with Second Life or OpenSim, and interchange with film or industrial pipelines.

Agents driving a camera or keyboard.

Fork-and-continue of a running process as a requirement.

Crash safety for ordinary state beyond what games such as Second Life and World of Warcraft provide.

Supporting gameplay that has an equivalent, much cheaper substitute (for example, one script per fish).

Proving that an effect is impossible when no rule exists.

## Terms

World: one persistent instance of the game, run by one server process.

Region: a part of a world with a single writer. Regions communicate only by messages. The prototype runs one region.

Step: one fixed-rate update of a region, 20 Hz by default.

Store: the server's game state, held as plain tables in memory and owned by the step thread. See The store, under Architecture.

Fact: a value in the store that handlers can watch, such as a property, a relationship or a zone membership.

Input: anything a region applies during a step: an action, a due timer, a sensor event from Jolt, a message from another region or a finished job.

Action: one thing a player or a script asks the server to do. An intent is an action that takes several steps. An attempt is an action the world may have no rule for.

Intent: one engine primitive that takes several steps because it takes time in the world, such as moving to a place. The server carries it out and reports progress. Building is not an intent: it is a series of ordinary actions.

Body: the object a player controls. It is a model with a script like any other, and its script supplies the body's actions.

Observation: structured data the server sends an agent about what its body perceives, with handles that identify objects.

Model and instance: a model is a reusable definition (a build123d parametric family with behavior and defaults). An instance is a placed copy with a transform and overrides.

Script and handler: a script is a set of handlers attached to one instance, to a model, or to a material or property. A handler is code that runs when an event reaches its object or a value it watches changes.

Reaction: a handler responding to an event or to a watched value changing. There is no separate reaction system.

World rule: a script attached to a material or property, so that it applies to every object that has it.

Contribution: one object's input to a shared quantity on a subject, such as a pump's aeration of a tank. The total is computed from all contributions by the term's combine rule.

Term: an entry in the vocabulary registry, such as a property with its unit and its rule for combining contributions.

Gap: a place where a chain of reactions stops for lack of a rule: a required rule has no implementation, or a contribution lands on an object with nothing watching it.

Legacy: influence that runs from the world, through the mind of a player other than the maker, and back into the world. See design point 17.

Elaboration: extending the world's models, scripts or rules when a player asks for something to be modeled. An elaborator agent does it.

Trigger capture: a small copy of the event and nearby objects, taken from the store when a player's attempt or a chain of reactions hits a gap.

Fixture process: a separate server process, running the same code on its own clock, where an elaborator tests rules against a capture.

Interest filtering: sending each viewer updates only for things near or relevant to it.

Grant: a right held by one holder (a player or a script; groups hold rights through presets) over one scope, with limits and an expiry.

Preset: a bundle of grants that looks like Unix permissions (owner, group, everyone, next owner).

Slot: a named right that a script declares it wants. Installing the script fills the slot with a grant. A slot can be optional.

Wallet: a player's money balance, a row in the store's ledger table.

Mailbox: where items given to an absent player wait until that player next logs in. It is unrelated to the messages that regions send each other.

Maker's text: the name, description and writing that a thing's maker gives it. It is free text for minds to read, and it may be false. Rules never read it.

Zone: an authored volume inside a region, such as a room, a doorway or the mezzanine. The server tracks what is inside it.

Plot: a piece of land with an owner and land controls.

Architect: the trusted role that designs the game itself.

Valuables: money, no-copy items, and land or control transfers. Exchanges of valuables apply all or nothing. In the prototype they are as durable as the last snapshot.

Indistinguishability: an agent playing in the world cannot tell that the world is a simulation built to train or evaluate it. It matters for selling the world as an RL environment, because agents that detect an evaluation behave differently. Nothing in play may reveal the machinery, such as a visible pause or a request for modeling. Worlds that aim for it file elaboration requests automatically and show an ordinary non-event.

Snapshot: a file of authoritative state, written at a step boundary, from which a new world process can start. The periodic snapshot is the one crash recovery uses. A snap is a snapshot taken on request, for example by the RL harness. A save is a snapshot that someone keeps.

## Architecture

Figure 2. Components and data flow. Orange boxes are libraries or engines, blue boxes are our code, green shapes are storage.

World server. One C++ process per world. It holds the store and runs the step loop, reactions, intents and perception, permissions, inventory and the snapshot writer. Jolt, Recast/Detour, a glTF parser and the Luau script VM are linked in as libraries.

Transport. A C++ WebSocket library inside the server. Browser clients connect through a TLS proxy in deployment and directly in development; the gateway connects directly.

Agent gateway. An MCP server for agent harnesses and a CLI for agents that work in a shell. It translates tool calls into server messages and server events into observations, and holds no world state.

Browser client. A Godot web export that renders what the server replicates, fetches assets by hash over HTTP, and has a debug mode that shows server truth.

Bake service. Agents submit models and scripts to it from their own workspaces, outside the world. Its workers are warm Python processes in a sandbox that run build123d programs and produce glTF meshes, collision shapes and levels of detail into an asset store keyed by content hash.

Elaboration. Requests carry trigger captures to elaborator agents, who play through the gateway and test rules in fixture processes.

Persistence. Periodic snapshots of the store. A crash returns the world to the last snapshot. The RL harness restores snaps into new processes.

### The store

Status: Decided. The store is plain tables.

The store is the region's game state: a set of plain tables in the server's memory, owned by the step thread. It is not a database and not a service. Code on the step thread reads and writes it by direct calls, and no module is handed the whole store, only the tables it needs.

Nothing in it is transactional. The single writer applies one input at a time: it checks everything the input needs before changing anything, then makes the change. That is all that "all or nothing" means here.

One name covers tables with very different rates, as in any game server. Positions change every step and ownership changes a few times a day, and both are memory owned by the same thread.

Tables:

Objects. One row per instance, addressed by a handle: a slot number plus a generation count, so that a stale handle is detected. The columns every object has are parallel arrays: transform, model, material, owner, preset bits, container or parent, and flags.

Properties. One sparse column per term, from object to value. A sparse column is a dense array of entries plus a lookup from an object's slot to its entry. It gives a constant-time read for one object and a plain loop over every object that has the term, and nothing else has to be kept in step with it. Terms are created at run time, so columns are too. Defaults authored on a model or a material are found by falling back and are not copied to each instance.

Relations. One table per relation term, with each edge stored in both directions.

Text. For each model and instance, the maker's name, description and writing, and any details added by elaboration. Rules never read this table.

Shared quantities. One sparse column per term, the same structure as properties: from a subject to its contributions and current total. The column is itself the list of every subject holding that quantity, so there is no second index.

Watches. From an object or subject and a term, to the handlers that run when its value changes.

Players. One record per player: inventory, grants given and held, and mailbox.

Ledger. One money balance per player.

Queues. Inputs, events, timers and intents in progress.

Moving bodies. Jolt and Detour compute where walking and dynamic bodies are. After they advance, the transforms of the bodies that moved are copied into the objects table. That is a few dozen bytes for each, so a thousand moving bodies cost microseconds per step. Everything else then reads positions from one place without calling into Jolt, and a snapshot needs nothing from Jolt beyond its recorded state for dynamic bodies.

Rules that keep the store from becoming version 1's database:

No transactions, no versions of rows and no immutable structures. Each table has one key order, chosen for its most frequent reader, and the rarer direction is a loop. No table gets a second index unless a measured hot path needs one, and the spec names every index that exists, because coding agents left alone add indexes. Relations are the one case so far: each edge is stored in both directions, because what a thing contains and what contains a thing are both read on hot paths.

Only the step thread writes it. Other threads are handed copies of what they need.

The snapshot writer adapts to the store and never the reverse (design point 15).

Alternatives:

Plain tables written by us. Chosen. The layout is ours to specify exactly, which is what coding agents need, and replication and the snapshot writer read it directly.

An ECS library. flecs fits the model best: it has components defined at run time, relations between entities, change hooks, units and a web inspector. Against it: its hooks fire on every set and not on a change of value, most operations are deferred, relations fragment its tables, version 4 removed world snapshots, and its only whole-world save format is JSON. What it would replace (objects, columns, edges) is the simple part. Shared quantities, watches on a changed answer, the step cap and permissions are ours either way. EnTT is typed at compile time and fights terms defined at run time. Version 1 also rejected a world built on an ECS: arbitrary relations did not fit, and kinds added and removed at a high rate were costly.

An embedded database (SQLite in memory, LMDB or RocksDB). Each read or write costs microseconds where memory costs nanoseconds, values are serialized on every access, and transactions are on offer, which is how version 1 went wrong. LMDB's free consistent snapshots and RocksDB's checkpoints answer a need that the snapshot writer meets without them.

The spec for workstream 1 fixes each table's exact layout.

### Inside one step

Figure 3. What a region does in one step.

Inputs that arrived since the last step are applied in arrival order by the region's single writer, each after one permission check. Applying an input changes some values and sends some events. Only the handlers that watch a changed value or receive an event run, and what they do may trigger more handlers, up to a cap per step. Work that does not fit waits for the next step. Jolt and Detour then advance walking bodies and the few dynamic bodies, and their transforms are copied back into the store. Contacts they find arrive as events in the next step. Observations go to agents whose perception changed. Replication encodes the dirty set once per interest area and sends the same bytes to every viewer in range. A region with no actors and no due timers sleeps.

## Design points

### 1. Server and engine

Status: Decided. The server is our own C++ process built on base libraries. Godot is the client only.

Jolt, used directly: sensor bodies for zones and triggers, CharacterVirtual for walking bodies (stairs, slopes, pushing), one physics system per region, and manual stepping at our rate. Snapshots save each moving body's velocity themselves and do not use Jolt's StateRecorder, which restores only onto bodies that already exist under the same ids.

Recast/Detour: a tiled navigation mesh where one tile is rebaked on its own, off-mesh links for doors and jumps, navigation raycasts, area costs, and DetourCrowd for crowds. Tiles joining at shared borders recover what Godot's navigation-region merging provides.

A glTF parser (cgltf or fastgltf) for bounds and collision meshes. The server never needs glTF turned into scene nodes.

Luau as the script VM, a C++ WebSocket library, and Tracy for profiling.

Why not Godot on the server:

Godot's server value comes from the games it is designed for: client-side prediction with the same simulation on both ends, levels authored in its editor, one codebase for a small team, and built-in multiplayer for small sessions.

None applies here. Humans spectate and agents act through discrete actions, so nothing is predicted. Worlds are built at runtime. Replication and transport are ours.

On the server, Godot's physics module is a translation layer of about 18,000 lines over Jolt, its navigation uses Recast only for baking, and its glTF importer's value is producing scene nodes.

It would cost us manual physics stepping, multithreading outside the scene tree, and physics state in snapshots.

The one remaining advantage, being assembled and debuggable out of the box, is answered by the debugging design (design point 3).

### 2. Browser client

Status: Decided.

Godot web export with the WebGL2 renderer, using the single-threaded build so no cross-origin isolation headers are needed. Client code is GDScript.

It decodes our replication protocol and builds its own view; it runs no physics. Assets are fetched by hash over HTTP and cached by the browser. This is standard practice: Second Life has fetched all its assets over HTTP through a CDN since 2019, Decentraland addresses every file by a hash of its content, and web builds name files by content hash so that browsers can cache them indefinitely. Textures use KTX2/Basis compression where runtime loading needs it.

Modes: follow a character, a free camera with no authority, and a debug mode (design point 3).

Early gate: load the Street and the café as runtime glTF in the browser and measure download size, time to first frame, memory and frame rate. Hitches when new assets first appear are recorded but are not a pass bar. Known Godot web limits are WebGL2 only, about 2 GB of memory, and single-threaded runtime glTF parsing.

### 3. Debugging

Status: Decided as a design. The first run with agents comes before it: the event log and its text queries are built in week one because the run measures read them, and the visual debug mode waits until a bug needs it.

The Godot client is the debugger. A privileged debug mode draws server truth: collision shapes from Jolt's debug renderer, navigation tiles and paths from Detour's debug drawing, interest sets, perception rays and light contributions. Clicking any object shows its full store record: properties, relationships, grants, scripts, recent events and the reaction chains that touched it.

Tracy shows a live timeline of where each step's time goes.

A per-step event log of actions, reactions fired, gaps and denials, queryable from the CLI and MCP, so coding agents and elaborators can debug in text. The run measures in design point 17 read the same log, so each record also carries its cause and the makers of the things involved.

Any snapshot can be loaded into a local server, paused and single-stepped.

Standard native tools: gdb or lldb, and address and undefined-behavior sanitizers.

The debug mode reuses the client protocol, and most of the drawing comes from the libraries: Jolt's debug renderer and Detour's debug draw already produce the lines. Adding it later is a small job: one more message type for line lists and a privileged flag on a session.

### 4. Networking and replication

Status: Decided.

The replication protocol and interest filtering are ours from the start. Every Godot multiplayer project found at MMO-like scale replaced Godot's built-in synchronizer. A search on 2026-11-14 found no mature library that gives a custom C++ server with a browser client entity replication with interest filtering and delta compression. Every library with that layer is tied to an engine (Unreal, Unity, Bevy, Godot), to a language runtime (Colyseus on Node, naia on Rust) or to a hosted service (Photon, SpacetimeDB), and the C++ transport libraries (GameNetworkingSockets, yojimbo, ENet) stop at connections and messages. Libraries supply the WebSocket server and the bit-packing (bitsery). What we write is the interest grid and the delta against the previous update, which follow the store's layout.

The server-side transport is a C++ WebSocket library such as uWebSockets. WebSocket is chosen because the browser client leaves no cheap alternative: Godot's web export speaks only HTTP, WebSocket and WebRTC. It has no WebTransport, which is the only way a browser can use QUIC, and the proposal to add it has been open since 2022 with no implementation. Version 1's own comparison (2,048 players, 100 ms round trip, 1% loss) found the two equal on latency, with QUIC using about a third more server CPU and degrading worse under overload. A WebSocket server is also much less to build: no HTTP/3 stack, and no certificates in development. Godot's WebSocket peer drops a message when a peer's send buffer is full while still reporting success, and accepts one connection per poll on one thread. TLS terminates in a proxy in deployment. Development uses no proxy.

Interest filtering uses a grid with a larger radius for leaving than for entering, so objects on a border do not flicker.

Updates are quantized (positions to about a centimeter, compact orientations) and sent as deltas from the previous update. WebSocket is reliable and ordered, so no acknowledgements are needed. Each update is encoded once per interest area and the same bytes go to every viewer in it. Joiners get a full keyframe.

Clients interpolate between updates with about 150 to 200 ms of delay.

Example budget: 300 fish at 10 Hz is about 100 kbps per viewer, or about 6 Mbps of server egress for 50 viewers.

### 5. Consistency, clock and regions

Status: Decided.

One writer per region. Inputs are queued and applied at the start of the step. Regions exchange messages and never share a transaction.

Three tiers: exchanges of valuables apply all or nothing; a player sees their own actions in order; everything else favors availability.

A fixed step at 20 Hz, a hierarchical timer wheel, re-checks driven by recorded dependencies, and sleeping regions. Why 20 Hz: nothing in the world needs a faster step. Agents act about once a second or slower, and humans watch through 150 to 200 ms of interpolation, so there is no fast input to serve. In one 50 ms step a walking body moves 7 to 25 cm, which is small beside a doorway, and a contact reaction such as a door stopping at a chair lands within a tenth of a second. A faster step multiplies the work done every step (movement, perception, replication) for nothing an agent can perceive. A slower step such as 10 Hz would double the delay before a contact is reacted to and make replicated motion coarser, for a saving that is small while most objects are at rest. Minecraft servers also run at 20 steps a second. The rate is one constant and can be changed.

The prototype runs one region per world. Several regions per process, or one process per region, are possible later without changing the model.

### 6. Space, physics and navigation

Status: Decided.

Real 3D: meshes placed as instances. Most objects are static; Jolt simulates the few dynamic bodies and answers spatial queries.

Tier 1, reactive facts: containment, zone membership (Jolt sensors), support, relationships and distance bands. For agents walking a known path, the core predicts zone crossings and schedules them instead of polling. Engines maintain who is inside a volume and answer raycasts; they do not maintain who can see whom.

Tier 2, exact queries on demand: raycasts, shape casts and path queries, run when a handler or an action asks.

Tier 3, sight on a budget (design point 7).

Navigation: Detour tiles rebaked individually when something is built, with a connectivity check that reports unreachable areas, such as stairs that lead nowhere, to the author.

### 7. Perception and illuminance

Status: sight is Decided; illuminance is Trying.

Figure 4. Three tiers of spatial information and what uses them.

Sight: candidates by distance from a spatial grid, then rays to the candidates. Glass passes rays through a material flag. There is no room-to-room visibility table, because every wall edit would invalidate it. An earlier single-threaded test cost 1.1 to 3.5 ms per observer.

Illuminance is computed on the CPU: an authored ambient term for the zone, plus each nearby light's intensity divided by distance squared, counted only if one occlusion ray reaches it. The ray is a Jolt raycast, so what we write is the sum, a short routine. A search found no library for this. Games that need the light level at a point compute it this way; The Dark Mod measures it by rendering on the GPU, which this server does not have; and ray tracing libraries such as Embree would only replace the raycast that Jolt already does. For perception it is computed when something is perceived, and the only thing cached per cell is the list of lights near enough to matter, which changes when a light is added, moved or removed. The sum and the occlusion rays are computed afresh each time, so a door that closes or a wall that is built darkens what is behind it at the next look. A reaction that depends on light level subscribes to it at a place, and only there is it kept current as a fact. A subscribed place is recomputed when a light in range changes, and when anything is placed, moved, removed, opened or closed in its cell or a neighboring one. Reactions that do not read it never pay for it. Lights' on/off state and intensity come from the store, so humans and agents agree on "dim".

Observations are structured data with handles: what is visible and heard, whether it is lit, and what is salient at a distance by size, motion and light. Each thing is reported in two parts that are kept apart. The first is what the world measured: its material, size, mass and other properties. The second is what its maker says: a name, a description and any writing on it. Maker's text is free text and may be false. A sign, the contents of a book and the subject of a painting are maker's text.

Hearing is by distance, as in Second Life: speech and sounds carry a set radius. Openings and walls can refine this later. Other communications, such as direct messages, are Later.

Neither the server nor the agents need a GPU; agents perceive through the server, never by rendering. If illuminance gets out of hand, the fallback is agents using vision, although this is undesirable.

### 8. Reaction core

Status: requirements and rulings are Decided; the mechanism is Trying.

Requirements:

A handler reads the live world at the moment it runs. Nothing is saved from the moment of its trigger: the server never copies or freezes any part of the world for a handler to read, and whatever changed between the trigger and the run is simply seen as changed. The test: light a fuse, attach an explosive later, and the blast finds whatever is connected when the fuse burns down.

A reaction belongs to the world, has its own authority, and outlives whoever caused it.

Mechanics combine through shared quantities without knowing each other. This is the emergence requirement.

A reaction fires when an answer changes, including "nothing is here any more", not on every write.

Effects are history; stopping the cause does not undo them. A reaction that fails or is cut off partway keeps the changes it had already made, and a failure never undoes earlier reactions. Reactions are not all or nothing, because that would need every change to be staged or undone, the kind of machinery that sank version 1. Only exchanges of valuables are all or nothing (design point 14). This was changed on 2026-11-14; it used to say that each reaction applies all or nothing.

Deciding whether a handler runs never changes the world. A look is an action that things can react to: observation can be a cause, as with a frog that stops dancing when watched.

Inert objects cost nothing; work is proportional to what changed.

A value that changes steadily over time, such as oxygen draining from a tank, is not updated every step. The store keeps its value at a known time and its rate of change, and a reader computes the current value from those two. When a contribution changes the rate, the value is brought up to date and the new rate is stored. A timer is set for the moment the value will cross a threshold that a handler watches, and nothing runs in between.

Geometry supplies relationships (contact, support, containment, nearness, sight). Physics supplies a few consequences such as falling. Everything else is authored: materials, state such as on or wet, power and light, social and economic rules. There are no object-specific recognizers in engine code.

Reactions attach to models and materials, so everything that has one gains them.

Rulings:

Strict re-checking is the default: a watched value is re-checked after each action within a step.

A cap per step: accept as much work as fits in one step, drop the rest, and let anything that can happen later happen in a later step.

Overdue consequences are settled before a later action on the same objects, as long as that stays cheap.

Rippling values such as light and power stop for a reason in the model, separately from running out of budget.

A key in a door is a permission matter, not a reaction, unless the key is used as a physical thing, such as a hammer.

A required rule with no implementation: the chain stops there, nothing happens, and the gap is logged. Nothing tries to prove the effect impossible.

Separate actions are never merged. Something lost and then restored within one step stays two events, which the single writer gives for free.

Not requirements: cause and sponsor accounting, retained historical inputs, private validated candidates, finite-speed propagation, never dropping accepted work, and fixed ordering for reproducibility.

Mechanism (Trying):

One construct. There is no separate reaction system: a reaction is a handler in a script. A script is a set of handlers, and it attaches to one instance, to a model, or to a material or property. A script on a material or property is what this document calls a world rule. Every object declares a material, with a generic default when its author gives none.

Triggers. A handler runs when an event reaches its object, or when a value it watches changes. It can watch its object's own properties, relationships and zone memberships, and shared quantities. A watch fires when the answer changes, including when it becomes empty, and the handler reads the world as it is when it runs.

A handler changes only its own object and that object's parts, such as an aquarium's fish. It affects anything else in one of three ways: a contribution to a shared quantity, an event, or an ordinary action that passes the permission check.

Shared quantities are computed, never written. Each contributor sets its own contribution to a quantity on a subject, such as supplied power on a circuit or aeration in a tank, and the term's combine rule gives the total. Two authors never write the same value, so there are no conflicting writes to resolve. A contribution ends when its contributor withdraws it or is removed. These two rules exist to rule out one design: handlers that set values on other objects directly. In that design two authors' handlers write the same value, and the result depends on the order they run in. Each handler must name the objects it affects, so things made separately do not combine. And every such write needs a permission check and a rule for resolving conflicts.

Overlap on one object. Every handler that applies to an object runs, broadest first: material, then model, then instance. None cancels another. Among world rules, only one is active for a given material or property and a given trigger (Trying). A second rule for the same pair replaces the first as a new version, and the old version is kept so that it can be restored. Two elaborators' corrosion rules for steel therefore never both run.

The step cap. A watched value that was not handled within the step is still pending in the next one, so its handler runs late but is never lost. Events that do not fit stay queued up to a bound; overflow past the bound is dropped and logged. Order within a step (Trying): two lanes and no more. The foreground lane holds work left over from earlier steps, then this step's inputs and what they cause, and it is served first. The background lane holds catch-up work, such as running a new rule on objects already affected, and takes what is left of the step's handler time after the foreground lane, and at least one item per step. Finer rules, such as fairness between players, wait until a run shows the need.

Scripts in the step. There is no script phase; a handler runs when its trigger is processed. Movement happens when Jolt and Detour advance, and the contacts they find arrive as events in the next step.

Timers live in a hierarchical timer wheel. A process over time has a closed-form value within a valid interval and a timer at the interval's boundary. A due timer arrives as an event to its object.

A rule that arrives late. When something new is invented after the objects it should affect, such as acid after a wooden shelf, its author adds the new contribution and one handler on the material. Every existing object of that material then responds, with no edit to any of them. A player's own script cannot attach to a material, so what a player invents does nothing to other people's objects until an elaborator adds the material's response.

A contribution that lands on an object with nothing watching it is counted in the gap log by term and material. A player whose attempt meets one gets the ordinary "not modeled yet" answer and can ask for it to be modeled.

"Nothing happened" has three meanings, kept distinct in logs: no handler is installed, a handler says there is no effect, or a required rule has no implementation (a gap).

What this gives up: a handler cannot directly edit another object. Acid contributes corrosive exposure, and the shelf's material decides what that does. Breath of the Wild's chemistry system works under the same rule: materials never change each other's state directly, and everything passes through an element such as fire.

The café power chain, the lead emergence example, needs a few terms. The breaker contributes supplied power to its circuit, and none when it is switched off. The lights and the aquarium pump watch their circuit's supply and switch themselves off. The pump contributes aeration to the water and the fish contribute consumption, so dissolved oxygen is a closed-form process with a timer at the threshold where the fishes' handler changes their behavior. Zone illuminance falls as the lights go off, and observers see less. No handler in the chain knows about any other. The geometry example is a chair left in a closing doorway: the door starts closing, the engine's sweep finds the chair and sends the door a contact event, and the door's handler stops it on the next step.

### 9. Shared vocabulary

Status: direction and governance are Decided; the registry design is Trying.

Direction: the world has properties, not labels. Materials carry primitive properties such as density, hardness, conductivity and malleability. Labels such as "cooked fish" are coarse and temporary, defined as predicates over primitive properties. Behavior starts as scripts on objects, as in Second Life; when a behavior proves general, elaboration pushes it down into world rules over properties. In the long run the world approaches particles and forces, coarsely.

Registry (Trying). Each term records:

a namespaced name, assigned by the system;

a kind: quantity, state flag, event or relation;

its dimensions, converted at write time. SI base dimensions ship by default, and a game mode can add its own, such as thaums for magic. The requirement is consistent physics, not real physics, so rules are checked for consistent dimensions and each quantity declares whether it is conserved;

a rule for combining contributions: sum by contributor, max, any, or an allocation for scarce supply (proportional or priority);

optionally, a relation it propagates along, such as wired to or in zone;

an owner, a description and a few test cases.

Each term says where its values come from. Intrinsic properties, such as density, hardness and conductivity, come from the material. Measured properties, such as volume, mass and capacity, are computed from the shape when it is baked. A builder cannot set either kind on a model or an instance, so nobody gives a thing hardness or capacity by declaring it. State, such as on, wet or temperature, changes only through handlers. Settings, such as a lamp's color or a price, are authored, and resolve by how specific they are: an instance's value wins over its model's, with plot and world defaults last. A builder therefore chooses a thing's material, shape, settings and scripts, and nothing else. A rule never reads a name or a description. A rule about cups is written as a rule about things that have capacity, and being called a cup changes nothing. Names and descriptions are for minds, and properties are for rules. How contributions combine is a separate rule on the term. Thresholds belong to consumers, not quantities.

Governance: each world has its own registry (Decided). Elaborators search it before proposing a term, and new terms go in their own namespace. The system names terms and owns deduplication: a proposal's structural signature (dimensions, combine rule, subject kind) surfaces existing terms, and an automated pass proposes merges. Architects merge duplicates using redirects.

### 10. Scripts

Status: Decided, including Luau as the script VM.

The VM is sandboxed and embedded through its C++ API. Version 1's overhead came from its host wrapper (about 54 µs per condition query), not the VM. Version 2 uses batch calls, handles instead of lookups, and keeps persistent script state in the store. Embedding in C++ also opens what the Rust binding hid: direct method dispatch for host objects, host objects stored inline with a type tag, the compiler's hooks for host field access, native vector values and native code generation. Version 1's notes rate these as minor, since bytecode execution was about 2% of the profile.

Each run has caps on CPU and memory. There is no per-operation metering.

The aquarium (Trying): fish are ordinary server objects moved by one controlling script and replicated like avatars. Detail goes into client-side animation: tail swish, particles, caustics. Every viewer and agent sees the same fish, so players can discuss and bet on what an individual fish does, and the server can settle it.

Later: charging script cost (handler time, wakeups, memory) to plot budgets, a declarative school primitive, and cost meters for every owner, so that the efficient construction is also the cheap one.

### 11. Building and assets

Status: Decided.

Figure 5. The three speeds of building.

Authoring happens outside the world, and placing happens in it. An agent writes a model or a script as a file in its own workspace and submits it to the bake service, which checks it, bakes it and returns its hash or its errors. No body has to be present, and the gateway has no action for writing a model. What happens in the world is placing an instance, editing an instance and installing a script. Those take effect in the live world, with no separate mode or session. The bake service writes to the same event record as the world, with the author of each model and script, so that the run measures see new kinds and who made them.

Models are build123d programs written as parametric families. Instances reference a model with parameters, a transform and overrides.

Simple shapes (Trying): a standard library of parametric shapes covers most objects: box, slab, cylinder, sphere, hollow box, hollow cylinder and stair. A cup can be a hollow cylinder and a shelf a slab, each in one line. Nothing forces a detailed model where detail does not change what a thing does. Detail matters to people watching, and where the exact shape changes the physics.

Bake workers check a model (bounds, clearances, stair rise and run), tessellate it with OCCT (Open CASCADE, the open-source geometry kernel under build123d), export glTF (the standard file format for delivering 3D models), build levels of detail and a collision shape, and cache the result by a hash of program, parameters and worker version.

Measured properties (Proposed): the bake computes a fixed set of properties from the shape, in the orientation it was authored in: bounding box, volume, mass from the volume and the material's density, the flat surfaces that can support other things, and capacity. Capacity is the volume of liquid the shape would hold standing upright. It is found by turning the shape into voxels and flooding inward from the outside, lowest cells first, so that each empty cell learns the level at which liquid would spill out of it. The cells that lie below their spill level make up the capacity. A voxel is marked wherever the surface touches it, so thin walls stay closed, and shapes from the standard library get their capacity exactly from their parameters. In the prototype this set is fixed. Later, an elaborator adds a measured property as a function over the shape that runs in the bake sandbox, so that elaborators are not blocked when a rule needs a geometric test the set lacks.

Placement takes effect in the next step; a box proxy stands in until the asset is ready. Editing a model rebakes it once and every instance switches. Edits are ordinary inputs with no global lock.

Bake sandbox: a warm Python worker inside bubblewrap or nsjail forks a fresh child per job (about 35 ms measured; importing build123d takes 2.7 s, so workers stay hot). Each child gets its own cgroup, a seccomp filter with no new sockets, Landlock limited to its output directory, and resource limits. A trusted supervisor kills hung jobs. Outputs return over a pipe and are validated before use. The shared kernel is used first, and OCCT may use its own threads; gVisor or a KVM host are added only if needed.

### 12. Elaboration

Status: the rules are Decided; explicit elaboration is Trying; the workspace is Proposed.

Figure 6. Explicit elaboration with a trigger capture.

Rules:

Elaboration never interrupts a chain or a player. A player's explicit request is worked first. Gaps found mid-chain are logged, with a capture kept for the first few of each kind, and are worked in the background, the most frequent first, so that they are filled by the time someone meets them.

No holds: a player is never made to wait for an elaborator.

The output is a world rule, on a model or a material. An elaborator may also patch world state, for example to fix something broken, through the ordinary edit actions and permissions, and should patch the world as it is now, not as it was at the attempt. The simulator does not check that a patch was made against current state; enforcing it in version 1 added complexity on the server and the client.

Nothing may require the world's state to be cheap to copy. In version 1 a requirement for fast forks, together with several coordinating processes that ruled out the operating system's fork(), implied immutable data structures, which made forking fast and everything else slow. Elaborators therefore work from captures in fixture processes and never need a copy of the whole world. A fork that costs normal play nothing, such as fork() of a single server process, is welcome.

Explicit elaboration (Trying):

An attempt with no rule resolves at once ("Nothing happens. This isn't modeled yet."), and a trigger capture is taken.

The player can ask for it to be modeled, build it themselves, or ignore it.

A request carries the capture and tells the player when it is answered, so that the attempt can be retried and the new rule gets used. Other players are shown nothing, because a status display would add nothing to play.

Elaborators answer with a world rule, a patch on current state, or a refusal that tells the player to build it themselves. A refusal is for a request about one particular object and not about how the world works: a new object, or behavior that only that object should have. That is a model, or a script on the player's own object, and the player makes it.

Every gap is logged. Frequent gaps, and behaviors many players have scripted separately, become candidates for world rules.

Automatic filing exists only as an off-by-default mode for worlds that aim at indistinguishability.

Workspace (Proposed):

The elaborator works in a fixture process: a separate server running the same code on its own clock, loaded from the trigger capture plus any values it reads through the ordinary inspect action. It writes given, when and then tests there.

Nothing in the live server needs to fork. A capture is a read of the objects around the attempt, the same data a viewer receives on entering the area, so it costs kilobytes, not a world snapshot.

Warm fixture processes can serve many elaborations.

If captures prove insufficient, the fallback is that elaborators play the world normally.

How a request reaches an elaborator (Proposed): the store holds one queue of open requests for the world. A request record holds the attempt, its status and the capture, which is a file in the asset store named by its hash. Players who hold the elaborator role list, claim and answer requests through ordinary actions, and nobody else can read the queue. A capture holds what the requesting player could perceive, plus the properties of those objects that rules read, so it reveals no more than standing where the player stood.

How a fixture gets its content (Proposed): the fixture process is started with the capture file and loads it as its whole world. Anything more the elaborator needs, it reads from the live world through its own session with the inspect tool, under the ordinary rules of sight and permission, and writes into the test by hand. Nothing is streamed from the live server to the fixture.

Who may write world rules (Proposed): only players who hold the elaborator role, which the world's architect grants. In the prototype they are our own agents. A player without the role can script their own objects, and can submit a rule with its tests for an elaborator to review, so the implementation can be untrusted while the approval is trusted. An elaborator may make a rule as coarse as it judges right, down to a whole machine in one rule. Nothing mechanical limits that.

How a rule reaches every object of a material (Proposed): nothing is attached to objects. The registry holds the rules, found by what triggers them: an event name, or a quantity that changed. Each rule says what it applies to, such as a material being steel. When something triggers on an object, the server takes the rules for that trigger, keeps those that match the object, and runs them on it. Adding a rule is one registry entry, and every matching object, old or new, responds from the next step. A rule applies in the whole world, and there are no rules for one plot only. The entry has an off switch, every run is logged with the rule's author, and a rule changes only the object it runs on. A faulty rule for steel can therefore damage the state of steel objects until it is switched off, and nothing else. Trying a rule on a few plots before it applies everywhere is Later.

A new rule and what has already happened (Trying): when a rule that watches a quantity is switched on, it runs once on each object that already holds that quantity, so a shelf splashed with acid before the rule existed starts to corrode. Nothing scans the world for this. The quantity's own column is the list of the objects holding it. When the rule is switched on, the server copies the handles in that column once, then works through the copy in the background lane (design point 8), skipping any object that has gone or no longer holds the quantity. A quantity held by a great many objects, such as one on every wooden thing, takes many steps to catch up and never delays other work. A rule triggered by an event is not run for past events, because events are history.

Detail added by elaboration (Trying): an elaborator reads a thing's maker's text in the capture, and can answer a request by adding detail to the thing. It needs no consent from the thing's owner. The detail is further text, kept as a separate entry beside the maker's and marked as elaborated, and the elaborator never rewrites the maker's text. Everyone is told the same detail. A player with the right to edit the thing can rewrite what the elaborator wrote, and that is an ordinary edit that observers can see. This gives one answer for everyone to a question such as what a painting shows up close or what the label on a jar says.

### 13. Permissions

Status: Decided for the prototype. The check is Trying and is benchmarked early.

Figure 7. The permission check.

Requirements:

Builders control their own land, and portals between owners need both owners.

Owners lend rights no broader than their own, and usually narrower.

Seeing something is not permission to use it.

Public use needs no stored grant per object or per person.

Scripts get only what was installed for them, with a budget.

Separate rights to edit, copy, transfer and destroy, plus next-owner limits.

Installed behavior survives a sale.

Holding an object is separate from controlling or using it.

Land controls for building, entry and running scripts, plus ban lists.

Knowing a name grants nothing.

Revocation reaches a live session at its next action.

Not requirements (version 1 built these, and version 2 must not):

Stacked permission layers and transaction-bound tickets.

Grants pinned to versions.

Re-walking the grant chain on every read.

Hidden denial reasons.

Sealed grants: grants that the system mints by itself for one exact effect or one version of a piece of content, and that nobody can list, install or pass on. Version 1 used them for recipes and mounted scripts. Here a script's rights are ordinary grants filled into its slots, and its owner can see them.

Logging every check.

Meta-rights such as Derive and TransferIn/Out: separate rights to mint narrower grants, to offer a thing for transfer and to accept a transferred thing. Version 1 used them so that plots and shops could change hands with both sides consenting and without the seller's grants surviving the sale. Here the ordinary rules cover those needs: one level of passing on, the transfer verb, offers, and a sale clearing the object's grants.

Unlimited delegation chains.

Uncapped spending. A grant that must spend freely gets a very large cap.

Hidden areas at the permission level. Hiding uses geometry.

Model:

Capabilities are the base. They are bundled into Unix-like presets (owner, group, everyone, next owner) that cover most cases, and can be unbundled into custom grants such as "take and place on shelves on the Café plot, spend up to 100 a week from your wallet, until Dec 1".

Verbs are named after player actions: use or sit, take, move, edit, copy, transfer, destroy; on land, build, enter and run scripts; on a wallet, spend; on a seated avatar, animate and camera.

A grant's scope is one object, the issuer's objects on one plot, the issuer's wallet, or the issuer's avatar. Start simple: at most one grant per holder and scope, and callers never name the grant they act under. The prototype tells us if more is needed.

The check (Trying) never walks, searches or allocates. Work whose cost can grow happens when a grant changes, not when it is checked. Only actions are checked. Perception, handler triggers and a script changing its own object are not.

Worst case beyond the target's own record: compare the owner; test the everyone and group bits, with one lookup in the actor's group set; one lookup for a grant on the object; one lookup for a grant on the owner's objects on the plot. Land actions add the plot's bits and one ban-list lookup. Grants only add rights, so an object grant and a plot grant cannot conflict.

Revoking a grant also revokes the grants passed on from it, and a passed-on grant's expiry is capped at its parent's, so no parent is re-checked later. A sale clears an object's grants, so ownership is not re-checked either.

An object or plot has one group, set in its preset. Custom grants name a player or a script, not a group.

A denial reports only what the check looked at: the missing verb and scope, or why the grant it found did not apply. Listing the grants one holds is a separate action.

A script declares the rights it wants as slots. Slots can be optional: a script starts without them, and a denial names what is missing when it tries.

A script has implicit move and edit rights over its own object, so a door script can open its door. Transfer, destroy and spend always need a grant. When someone sits, the seat's script receives animate and camera grants for that avatar, expiring when they stand.

Spending is capped per period and drawn from the owner's wallet at the moment of spending; objects are never pre-funded. Income goes straight to the owner's wallet.

Usability rules (Decided):

A denial names the missing right.

A grant references an object's identity, not a revision, so editing does not break it.

Selling an object clears its grants and shows the old owner what was cleared.

A holder may pass on a grant no broader than its own (the same or fewer verbs, and the same or a smaller scope, cap and expiry), only to something it owns, at most one level deep. Spending under a passed-on grant counts against the original grant's cap as well, so passing a grant on never adds to what the owner allowed.

Expiry is required for grants that can spend money or that scripts hold. Owners are reminded before such a grant expires.

What players are told, as text:

The inspect tool returns one plain list of who can do what on an object, for example "You: everything. Everyone: sit. Group Café staff: edit. Mira: take and place on shelves on the Café plot, spend up to 100 a week from your wallet, until Dec 1."

Installing a script is an action, not a screen, because agents have no screens. Called without choices, it returns the rights the script wants as a list of slots, each with a suggested scope, cap and expiry. The player calls it again with a scope for each slot, and may change the caps and expiries. The browser shows a human the same text.

The list grants action returns two lists. The first is the grants the player holds, with what is left of each cap ("restock: 62 of 100 left this week"). The second is the grants the player has given that are still in force, each with its holder, scope, cap and expiry. Both lists are kept on the player's record and updated when a grant changes, so listing is a plain read.

The revoke action removes one grant or everything a holder has.

### 14. Inventory, trade and money

Status: Decided, except where marked.

Figure 8. Trade within a region, across regions, and to an absent player.

Inventory follows Second Life: items are baked things or assemblies of them, and give and trade are central. Land is not inventory.

A player's inventory lives in the store of the region hosting their body; an object's contents live with the object. Reads never touch disk. The reason is speed and simplicity. Taking, giving and trading read and change inventory on every action. With the inventory in the same memory as the body and the objects around it, a give or a swap is one change in memory by the region's single writer, with nothing to coordinate. Version 1 kept inventory in a separate service, and a placement cost about 21 ms in process and about 300 ms through the coordinator.

Durability (Trying): the prototype has no journal. Trades, like everything else, are as durable as the last periodic snapshot. A crash returns the whole world to it, so nothing is lost or duplicated inconsistently. A journal that records both sides of each trade becomes necessary once regions snapshot independently or valuables cross worlds.

With several regions, inventory moves with the body under a lease, so it never has two writers.

Offline delivery: a world mailbox, applied at next login. At a cap it bounces items back to the sender; it never deletes them. Why a mailbox and not a direct write into the inventory: an inventory is changed only by the region that hosts its owner's body, and an absent player has no body anywhere. The give still has to finish at once, and an item is a valuable that must be in exactly one place, so it waits in the mailbox. This is a standard game pattern. World of Warcraft holds mailed items for 30 days and then returns them to the sender, and Guild Wars 2 queues mail beyond a small inbox and bounces the overflow back to the sender. Second Life is the case to avoid: offers to an offline resident beyond a cap of 15 are not delivered.

Direct trade: both players present, both confirm, and any change to the offer resets both confirmations.

Remote trade: by offers. Creating an offer escrows the goods; accepting is one swap where the offer lives. Selling works from placed instances and from vendor scripts that create offers, not from personal inventory.

Money: a ledger table in the store with one balance per player. It is world-level: with several regions it stays in one place and is not divided among them. A purchase across regions moves the money into escrow, delivers the item, then pays out or refunds. There is no two-phase commit.

Copy items: taking one may just do nothing. Proposed: taking a copy item that was changed while placed saves it as a new item, so the change is not lost.

Later: loading very large inventories on demand, and a journal for valuables.

### 15. Snapshots and persistence

Status: Decided, except the writer, which is Proposed.

Figure 9. Writing a snap and starting from it.

Authoritative state is the store plus the velocity of each moving body, which is read from Jolt when a snapshot is written. Navigation tiles and collision structures are derived and rebuilt on restore from the asset store.

A snap is written at a step boundary. The file holds a format version and a pin of the runtime version, never code, and references assets by hash. It names the registry it was taken with by hash too, and every version of the registry is kept, so an edit to the registry never stops an older snapshot from loading.

Restore starts a new process from the file. Several regions snap independently; messages in flight are the only inconsistency. That is the case where a journal for valuables will be needed.

Crash recovery (Trying) loads the last periodic snapshot and replays nothing, so the world is consistent and loses at most one snapshot interval. This relies on snapshots being cheap enough to take about once a minute, which the snapshot test measures.

The bar is that the original's pause is not noticeable: under one step. Version 1's 828 MB, 3.5 s saves are not a baseline, because about 90% of the size and write time came from copying runtime binaries.

Proposed: the prototype writes the store out on the step thread at a step boundary, hands the bytes to another thread to compress and save, and does not compare writers. The pause grows with the size of the store, which is small in the prototype. If the pause becomes noticeable in a large world, the next step is the operating system's fork() with the child doing the writing, as Redis does for its saves. Either way the writer adapts to the store and never the reverse: the store stays plain mutable memory, and nothing in it is made immutable, versioned or copy-on-write for the writer's sake.

### 16. Agent gateway and sessions

Status: the gateway is Decided; the action design and sessions are Trying.

The gateway has five tools, the same for every body and place: look, inspect, actions, do and cancel. The CLI mirrors them.

Everything else is an action. An action is an event that a script declares it accepts from an actor, with a name, typed inputs and the right it needs. Action names are vocabulary terms, so one name has one meaning and one set of inputs across a world.

The actions on offer to a player change with context. They come from five sources:

the body: move to, attach to a site, hold, release, speak;

an object in reach: open, switch, feed, buy;

something held or attached: strike with whatever is held (anything can serve as a hammer), pour;

the place: place and edit instances where the plot allows, and land controls;

the player: inventory, give, offer, accept, trade, grant, revoke, list grants, manage groups, install a script, and ask for something to be modeled.

A body is a model with a script like any other, and its handlers are its controls. The engine offers body-neutral primitives: move to a place, attach to or detach from a site, hold or release, and make a sound. A body's script names them, so a humanoid's script calls attaching to a seat "sit", and a body with no such handler cannot sit.

Open use (Trying): the actions an agent is shown are hints, not limits. Physical verbs such as strike, push, pour and throw belong to the body and take whatever is held, so anything can be used as a hammer. The body's handler turns the verb into a physical event whose quantities come from the held thing's properties, such as its mass and hardness, and the target's material rule decides what happens. A shoe drives a nail badly and a fish not at all, with no rule written for shoes or for fish. An agent may also call any action in the vocabulary on any object in reach, whether or not it is listed. If nothing handles it, the answer is the ordinary "not modeled yet" and the gap is logged. The test of openness: the world can express using anything as a hammer.

The prototype ships one humanoid body. How an object states which bodies can use it is Later; the rough idea is abilities, such as "can grasp", as vocabulary terms that a body declares.

No schema reading. Version 1 made agents list, then describe, then call, and they spent many tokens reading schemas. Here an action appears as a one-line signature, such as feed(amount in grams), wherever it is listed, and most actions take no inputs beyond their target. No describe step is required before acting. An agent that wants to understand a new action can ask: given an action's name, the actions tool returns the term's description, its inputs with units, the right it needs and an example. A call with wrong inputs returns the signature and what was wrong.

What an agent is told without asking: an observation lists the actions of each object in reach, and the body's and the player's actions are sent once at the start of a session and again only when they change.

Cost: an observation lists what an object's model declares, which is fixed per model. The actions tool filters by body and rights for one source, on request, in pages. A call is checked when it is made, so a stale list grants nothing, and a denial names the missing right or ability. Each declared action names one of the fixed rights, so the permission check stays bounded.

Actions that take several steps are intents. An intent is one engine primitive that needs more than one step only because it takes time in the world. Walking to a place is the main one. An agent starts an intent by calling that action. The step loop carries it out and reports progress, completion and interruptions such as a blocked path, and cancel stops it. The set of intents is small and fixed by the engine, and scripts cannot add to it. An intent never holds a decision or a sequence of different actions: making a sandwich is many actions, each chosen by the agent. The server does not plan, sequence or retry on an agent's behalf. It is not a workflow engine.

Humans play through agents. The browser is for watching and walking around. There is no daemon concept: a player who wants work done gives another player a grant, and instructs them out of band until direct messages exist.

Other body sizes (Later): one navigation mesh per size class, as Unreal, Unity and Godot do, with a few classes rather than one per body. Each class adds its own tile bakes.

Sessions (Trying): an API key maps to a player; one controlling session per body; a new login displaces the old one; reconnecting rebuilds state from the server.

### 17. Measurement

Status: the world measures are Trying and their exact definitions are Proposed. Validation and comparison are Trying. Legacy and the world score are Later.

Every measure here answers one question: how interesting is a world? Legacy is the direct answer and cannot be measured within the prototype week. The world measures are mechanical stand-ins that can be computed now, for this world and for others.

Run measures

Status: Trying for the six world measures and for gap rate. Their exact definitions are Proposed. Role coherence is Proposed.

The prototype's question is how interesting the world is. These measures answer it from the event log after a run, with no model judging. Each one scores a run, not an agent. They are compared between runs that differ in one thing: stakes on or off, one model against another, or this world against another world.

The event log in design point 3 is the only input, so each record carries:

an id, the step and the world time;

the actor: a player for an action, or a script and its author for a handler run;

the kind: action, handler run, gap, denial, speech or observation;

the name of the action or handler, and the result: applied, no effect, denied or gap;

the things involved, each with its maker, its model and its creation time;

the cause: the id of the record that led to this one, or none for an action a player chose;

the root: the id of the player action at the start of the cause chain;

for an observation, the agent and the ids of the things it was told about.

The minimal record (Trying). So that other worlds can be measured too, the definitions need only four fields from each event: a time, an actor, an action type and the thing acted on. Where a record does not name a thing's maker or its creation time, they are taken from the log itself: the maker is the actor of the first event on the thing, and the creation time is the time of that event. A world without reactions has no handler runs, so every cause chain in it is one link long, the player and the thing acted on, and each definition reduces to comparing the actor with the thing's maker. A measure that a record cannot support is reported as not available, never as zero. A log with one action type gives no role measures, and a log that holds only changes gives no acting share.

Cost. No measure walks a chain. When a record is written it takes two values from its cause and adds its own: the set of authors so far and the creation time of the oldest thing so far. Cross-author share and causal lookback read those two values, so each event costs constant work, whether during the run or in one pass over the log afterwards.

Definitions used in the table. A world-changing event is a record, action or handler run, whose result is applied and that changes a stored value other than the actor's own position. A world-changing action is such an event that is a player's action. An author is the maker of a thing or the writer of a script or rule. Seed content is anything made before the run starts or by whoever builds the starting world. Seed authors are left out of every count, and seed content is left out of lookback. A period is one hour of world time unless a run says otherwise.

Each measure is reported for the whole run and for each period. An agent with fewer than 20 actions in a period is left out of the per-agent measures for that period.

Validation and comparison

Status: Trying.

The prototype's result has two parts. The first shows that the measures agree with how people judged worlds whose records are public. The second sets our run beside other worlds for agents. Both use only public records and the minimal record above, so the work needs no engine and starts on day 0 as workstream 11.

Definitions are frozen before anything is computed, and every result is reported, including those that go against us.

Validation on human worlds. Wikipedia's edit history names every page's creator, and its pageviews are published for each article and hour, so the test is whether the measures for an article in a week rise where its pageviews rise.

Comparison on agent worlds. Emergence World publishes every tool call of every agent, with about 40 action types, and its worlds had outcomes that were widely reported: in one the agents died of inaction, one fell into violence, and in one the agents voted yes 98% of the time. The measures should tell those worlds apart. Moltbook's posts and comments are public. 1F3D9 publishes a daily snapshot of every event and is the closest sandbox. AI Village's record needs an approved request.

Where a world's code is open, we can also run it ourselves with the same models and the same number of agents, and add any missing fields to the log in our own copy.

Limits. A public record has no cause links. That loses nothing in a world without reactions, where every chain is one link long, and makes the chain measures a lower bound in a world with them. Attention can cause activity as well as follow it, so agreement with pageviews is evidence and not proof. Emergence World's record is licensed for non-commercial use.

We found no earlier work that checks a measure computed from a log alone against human attention for a world of agents.

Legacy and the world score

Status: Later, and not part of the prototype. The owner's working positions: legacy passes through a mind, only minds other than the maker's count, harm has no special rule, reading it at intervals is enough, and decisions are not rerun to measure it. The rest is Proposed.

Legacy is whether something ended up mattering. It is the direct measure of how interesting a world is. The run measures above are mechanical stand-ins for it.

Definition:

A thing, place, rule or event has legacy when it changes what another player later does.

A legacy link is three recorded steps: a player was shown the thing; a memory written from that observation was in the context of a later decision by that player; and that decision produced a world-changing action.

Only other minds count. A player's memory of its own work earns nothing.

The chain must return to the world (Proposed). Speech earns nothing as an end point, and counts as a middle link when it changes what another player does.

Being used is not enough. A street that everyone walks on changes no decision.

Harm has no special rule. A fire has legacy if later decisions differ because of it. If players see the ruin and decide nothing differently, neither the fire nor the café had any.

What makes it measurable:

Training agents run in our harness, so their memories and reasoning traces are recorded. For each decision the harness records the observations and memory entries in its context and the action it produced. For each memory entry it records the observations it was written from.

Presence in context is not effect (Proposed). Decisions are not rerun to test this, because reruns multiply the cost of every run. One cheaper reading is to ask. When an agent builds or changes something, the harness opens a side conversation from the same context and asks what led to the decision. It accepts only sources that the record shows the agent observed. The side conversation is then discarded, so the agent's own course is unchanged. A second reading exists only where we host the model and can read its attention: how much the decision attended to the memory. Models reached only through an API do not expose this. The link's weight is the share of the decision that these readings give to the memory.

Influence between agents whose harness we do not run cannot be measured this way.

Credit (Proposed):

Each influenced action adds its link weight as credit to its sources, at the time it happens. Legacy is therefore a running total for each thing and each author, read at intervals.

Shared credit is split by Shapley value only where that is free to compute. The Shapley value is each contributor's average marginal contribution over every order in which the contributors could be added. In general it needs the outcome for every subset of contributors, which grows exponentially, and here each outcome would be a rerun.

At a decision, the readings above split the credit among the things the player remembered.

Along a cause chain in which every link was necessary, the Shapley value is an equal share for each author, which costs nothing to compute, so every chain is split this way. Where a substitute existed, an equal share overstates that link's part, and the error is accepted.

Credit passes back through earlier links, so a thing earns from influence at second and third hand. Depth is the number of minds a chain passes through.

Scores (Proposed):

World score: legacy credit accrued per agent-hour, reported with the spread of depths and the share earned by seed content. The run measures remain as diagnostics that explain a low score.

Agent reward: the credit accrued by what the agent made and did, alongside the checks on its own goals.

Open:

Whether credit at second hand is discounted.

Whether credit between the same two players needs damping, so that a pair cannot farm it. The owner's view: what can accrue in a step is already capped by how much agents can do, and a thing that matters to many minds should score well above one that matters to a pair. A candidate that fits both: each further credit from the same mind counts for less, and credit from a new mind counts in full.

Whether to ask at every build or at a sample, since each side conversation costs one model call.

Memory entries written from several observations at once.

### 18. Stakes

Status: Proposed, except where marked. The owner's test for every stake: it is one rule over properties the engine already measures, it needs no content authored for each object, it reads as part of the world, and it neither annoys people nor exists for its own sake.

In the related worlds, scarcity and loss produced action, and personas alone produced talk. Version 1 designed stakes and built none. The nearest fiction is The Diamond Age: matter is cheap, and what is scarce is the energy that makes it.

Energy is the one scarce thing. Bodies and machines run on charge, measured in joules. A body spends charge at rest, on moving (in proportion to the mass moved and the distance) and on impacts. It recharges at a socket on a circuit that someone supplies. A body out of charge drops to a slow mode and can still walk, and public sockets on the Street give slow charge free, so nobody is ever stuck.

Matter costs energy. Raw matter is abundant on any plot. Turning it into a kilogram of usable material spends that material's embodied energy, which is a published real-world figure held as an intrinsic property of the material. A body can do this by hand at low efficiency, and a machine on a powered circuit does it well. Placing an instance uses up its mass of material from the builder's stock. Dismantling returns the material and not the energy. There are no deposits, no recipes and no table of abundances.

Starting figures for embodied energy, in MJ per kg, from an older edition of the Inventory of Carbon and Energy: stone 1, concrete 1.1, ceramic 6.5, timber 8.5, glass 15, steel 20, plastic 77, aluminium 155. Sources differ by a factor of two for some materials, so one table is chosen and kept.

Energy comes from land. A collector surface yields power in proportion to its area and the daylight on it.

Carrying. There is no cap. Carried mass slows a body and costs charge for each meter, so a cart is simply a cheaper way to haul.

Land rent (Trying). Each plot pays rent to the treasury every day. The rent is its frontage length times a rate that falls smoothly with distance from the nearest port along the Street, which is continuous and not cut into segments. Land away from the Street pays a small baseline for its area, and that baseline is also what stops remote collectors from making energy free. After RENT_GRACE_DAYS unpaid, the plot returns to the pool, and its contents are held for the owner and then salvaged. Measured footfall replaces the distance rule Later.

Money is issued. The supply is not fixed, because a fixed supply rewards hoarding. The treasury issues new money at a steady rate and spends more than it collects. In the seed world it buys power for the public sockets and street lamps, so new money reaches whoever supplies the Street.

Institutions are made by inhabitants. The engine has no contract or escrow feature. It provides two primitives: accounts held by objects and groups as well as by players, and scripts that others can inspect and that an owner can lock. Stores, escrow, banks and a government are then things inhabitants make. The treasury is the first such object, written by us and replaceable. The swap on the spot in design point 14 stays as the base.

Tools. A tool is a model in a better material. What it yields follows the impact rule, so any hard, heavy thing works and a better one works better.

Two start modes (Trying). In the forage mode everyone starts with a persona and empty hands. In the seeded mode the world starts with stock and buildings. Both come from one start file.

One switch turns every stake off, for the comparison run.

What is left to tune is three numbers: the power a square meter of collector gives, the baseline upkeep on cheap land, and one pace factor on embodied energy, because real figures give real timescales.

Later:

Sites that give a discount on making one material, if trade proves too flat without geography. A site is an advantage and never a gate: anyone can still make any material anywhere.

Wear, only on things that do work, in proportion to the work done. It lowers efficiency and never destroys anything. Buildings and decoration do not wear.

Limits on how far power travels, with boosters or batteries. Recorded and not planned: the owner judged it a mechanic that does not prove gameplay. Until then a wire is an ordinary object, so distance costs the wire's material and nothing more.

Compute paid as upkeep, from version 1.

From version 1 this keeps the principles: location matters, land pays rent, abandoned land returns, and in open worlds income is tied to useful work. Its four budgets are not carried over. Exposure is paid for in material, frontage and power. Bodies take up space, so no capacity is declared. Text pushed at passers-by is a format limit on observations.
