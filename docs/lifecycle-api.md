# Assembly lifecycle

`server/lifecycle` owns object allocation and the declared-part graph. It reads catalog definitions to expand a model into its root and named ordinary child instances. It does not implement construction costs, permissions, physics, scripts, trading or persistence orchestration. Only its allocation/removal functions and store/object snapshot code accept the full object table.

There are two different graphs. `Parts` and `declared_parts` describe authored CAD membership. The ordinary parent column also describes grasp, seating and inventory custody. Collecting an assembly follows declared membership only; sitting on, holding or storing something never makes it part of a model. An assembly's named children have their own ordinary generation handles and default materials. The root's explicit material override applies to the root; child defaults retain the author's per-part materials.

Creation accepts a validated root initialization from a trusted action/content adapter and an immutable catalog expansion. It returns every created handle for the separate space, reaction, observation and record adapters. Those adapters preflight/import their assets before allocation. Allocation does not emit gameplay events or run callbacks. The authenticated action fills owner/maker/time; client-provided metadata cannot override them.

Parameter replacement first produces a plan without changing any row. Match children by declared name, retain matching handles, create newly added names and retire removed names. It supports an empty, solid or logical root and changes in part topology. Matching parts retain their attribution, instance state and authority; their model/material binding and authored local transform change. A part's explicit instance material override is retained when its old material differs from its old model default. Root authority, attribution, placement and explicit material stay unchanged unless the edit explicitly supplies a replacement material. The construction-law adapter evaluates the complete old/new material mass before committing any resource exchange.

The caller retires the plan's removed subtrees before applying replacement. Applying a stale plan is an internal error, not a partial edit. The single writer does not yield between plan, narrow module preflights and commit. There is no transaction manager or live-world snapshot for an ordinary edit.

Removal has two explicit owner operations. `Instances::closure(roots)` collects the live, deduplicated declared-part closure without changing it. `Instances::release_rows(closure)` removes incident declared edges/names and frees slots only after the integration owner has finished every other subsystem's cleanup. Lifecycle retains no reaction, permission, physics or presentation tables and runs no callbacks. The fixed integration order is documented in [Object lifecycle and scene integration](scene-api.md).

The alternative of having lifecycle retain every subsystem table would give the allocation owner unrelated authority. Freeing slots and notifying owners afterward would allow generation reuse before stale offers, state and colliders were removed. The integration owner performs the required ordered work while identities remain valid, then calls the narrow allocation owner once.

RELS appends the named-part rows. Names and handles are authoritative; the declared relation and sparse lookups rebuild on read. Capture filtering includes selected live rows and selected child endpoints only. Tests cover transforms under rotation, variant topology and preserved handles/authority, logical roots, material defaults/overrides, removal that excludes unrelated occupants, exact closure/release and generation reuse. Integration tests additionally exercise actual geometry/script reinstallation, hidden visibility, cleanup ordering and construction-law resource settlement.
